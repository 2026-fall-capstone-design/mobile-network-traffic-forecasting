# 635–637. 관계 점수 실행의 저장 오류와 부분 예측 복구

## 무엇을 계산하려 했는가

과거 target의 시간대별 24차원 profile을 정규화하고 cell마다 8개 이웃을 먼저 검색한다. 후보 쌍의 입력 지원을 확인한 뒤, 각 cell과 이웃 query에 대해 Tab/HGB의 9분위수를 추정한다. 양쪽 cell·양쪽 절반마다 지원 입력 8개 이상과 관측 날짜 2개 이상이 필요하다.

9분위수 사이의 선형 CDF로 혼합 중앙값을 구하고, 관측 query 정답을 사용하는 관계 점수를 집계한다. cell 두 쪽의 평균에 같은 비중을 주고 양의 부분을 비용으로 쓴다. 이 비용이 작다는 것만으로 두 cell의 관계가 같다고 인증하지 않는다. 식과 이동 조건은 [638 기록](0638-numeric-precision.md)에 정리했다.

## 실제 실행과 복구

| 기록 | 관측된 결과 | Tab context / query | 새 HGB fit | 실제 시간 |
|---|---|---:|---:|---:|
| 635 | 첫 확률 저장에서 인자 이름 충돌. 결과 배열 미저장 | 0 / 0 | 지원 분류 1 | 3.9190269초 |
| 636 | 79쌍 검색·22쌍 지원. 5개 cell 출력 저장 후 controller의 `meter.json` 읽기 오류 | context 6 완료, query 1,984 시도·1,856 저장 완료 | 지원 분류 79 + 분위수 45 | 80.8135497초 |
| 637 | 누락 9개 cell의 예측 완료. 기존 5개 cell과 분류 출력 재사용 | 새 context 9 / 새 query 1,856 완료 | 분위수 81, 지원 분류 0 | 111.5746071초 |

세 실행의 시간 합은 **196.3071837초**이며 실패 비용도 포함한다. Tab context는 중단된 작업을 포함해 15회 사용했고, 고유하게 완료된 cell context는 14개다. 최종 저장된 분위수 query는 모델별 3,712행이다. Tab query 시도 합 3,840행에는 중단된 128행이 들어간다. HGB fit 합 206회에는 635의 저장 실패 분류 1회가 들어간다. 행·context·fit·기록 번호를 각각 별개로 센다.

635의 오류는 `save(p, **kw)`의 첫 인자와 `p=확률배열`이 겹친 `TypeError`다. traceback은 확률 계산 뒤 저장 호출에 도달했음을 보여 준다. 메모리에서 계산한 128행은 저장되지 않았고, meter의 확률 query 값은 갱신 전 파일이어서 0이다. 이를 “확률 계산 자체가 없었다” 또는 “저장된 128행을 복구했다”로 바꾸지 않는다. [오류 원문](../evidence/0635-0638/originals/SRC-0024140.json), [코드](../evidence/0635-0638/originals/SRC-0022528.py.txt), [정산](../evidence/0635-0638/originals/SRC-0024137.json).

636은 helper의 인자 이름만 `path`로 고쳤다. 이후 발생한 `PermissionError`는 controller의 상태 파일 읽기 오류다. 모델 적합 실패라는 증거는 아니다. 여섯 번째 cell의 context 준비는 끝났지만 진행 중인 128행 예측과 KV 상태가 저장되지 않아, 637에서 해당 cell 준비를 다시 해야 했다. [복구 코드](../evidence/0635-0638/originals/SRC-0022530.py.txt), [실행 로그](../evidence/0635-0638/originals/SRC-0024248.json).

637은 상태 파일 읽기에만 최대 1초 동안 5ms 간격 재시도를 적용했다. 기존 지원 분류 79개와 cache index `0,1,2,3,5`의 Tab/HGB 출력 1,856행을 재사용했다. 아카이브 검수에서도 79개 확률 파일과 5개 cell 파일의 바이트 일치를 확인했다. 새로 실행한 것은 나머지 9개 cell의 Tab context·query와 HGB 81 fit이다. [637 코드](../evidence/0635-0638/originals/SRC-0022527.py.txt), [결과](../evidence/0635-0638/originals/SRC-0023965.json), [아카이브 수치 검수](../verification/pilot-001.md).

## 당시 판단과 후속 정정

637의 저장 결과는 공통 유효 edge 2개에서 Tab/HGB 모두 UPC 소속을 유지했다. 원래 사전 분기는 Tab이 UPC를 유지하면 이 조합을 닫도록 설계돼 있었다. 그러나 이때 Tab의 float32 분위수와 HGB의 float64 분위수에 같은 root 잔차 조건을 적용하면서 수치 유효성이 크게 달라진 문제가 발견됐다.

따라서 637의 `Tab_keeps_UPC`는 보존하되 확정적인 방법 기각으로 사용하지 않는다. [638](0638-numeric-precision.md)은 같은 저장 예측을 float64로 계산해 22개 관계와 서로 다른 소속을 확인했다. 이는 앞선 실패를 삭제한 새 성공 실험이 아니라 같은 명세의 수치 정정 이력이다.

## 팀이 재사용할 것과 남은 범위

완료된 14개 cell의 9분위수, 79쌍의 검색·지원 목록과 분류 출력, 수정 전후의 graph 비용은 [근거 묶음](../evidence/0635-0638/README.md)에서 찾을 수 있다. 파일 ID·원래 경로·해시·같은 사본 관계는 [출처 안내](../sources/pilot-001.md)에 연결했다.

같은 자료·cell·query 순서·모델·분위수·지원 규칙을 사용하는 검토라면 이 완료물을 먼저 확인한다. 새로 설계할 실험은 어떤 조건이나 질문이 바뀌는지 기록한다. 정밀도 문제를 확인하려고 기존 모델 추론부터 반복할 필요는 없다. 보존 코드의 실행 명령은 과거 기록이며, 이 아카이브는 실행을 지시하지 않는다.

이 묶음에는 최종 RCTL 성능, 새로운 도시·cohort·seed 일반화, 통계적 유의성, 방법의 신규성 검증이 없다. 636에서 재사용한 5개 cell의 정렬 전 HGB 분위수 crossing 수는 이번에 확인한 완료 요약에 기록돼 있지 않다. 637의 `crossing_rows`는 새로 계산한 9개 cell 범위라는 점을 유지한다. 616의 전처리와 633의 초기 소속 근거는 별도 검토를 이어간다.
