# 52·54. 자료 적합성과 부분 관측 복원: 확대 기준 미통과

2026-09-26의 52·54 계획과 실행을 정리했다. 52는 Beijing 공개 자료의 스키마 확인이고, 54는 Milan의 관측값 일부를 가린 현재값 복원이다. 54의 TabICLv2는 평균·양쪽 기간·셀별 비교에 관한 사전 확대 기준을 통과하지 못했다. 앞 구간의 이득은 남아 있지만, 관측 지점 선택·clustering·미래 RCTL 예측으로 확장할 근거는 확보하지 못했다. **개발 자료의 작은 확인이며 독립 test가 아니다.**

[출처와 열람 범위](../sources/history-031.md), [원본·재사용 자료](../evidence/0052-0054-partial-observation/README.md), [22개 주장 검수](../verification/history-031.md)를 연결했다. 55번의 수치·실패·비용만 여기서 통합하며, 51·53의 문헌과 55의 전체 신규성 판단은 미완료다. 정리 과정의 새 모델 학습·추론·forward, 원 연구 스크립트 실행, 난수 생성은 없다.

## 52. 공개 Beijing 부분집합으로 확인한 것

[공식 README](https://raw.githubusercontent.com/tsinghua-fib-lab/STK-Diff/e1faed12aa7abb33d801fe9483026769ffaeeed3/README.md)는 STK-Diff에 Beijing 기지국의 집계 5G 트래픽 일부를 제공한다고 설명한다. 고정 commit은 `e1faed12aa7abb33d801fe9483026769ffaeeed3`이다. README의 `traffic_data/bs_beijing.npz`와 달리 저장 Git tree 및 [loader](https://raw.githubusercontent.com/tsinghua-fib-lab/STK-Diff/e1faed12aa7abb33d801fe9483026769ffaeeed3/dataset_loader.py)는 `traffic_data/beijing.npz`를 쓴다.

원래 내려받은 NPZ는 1,413,636 bytes이며 Git blob SHA-1은 `8ab4fee3eeb542ef25eb3a3c9bc51091189d2c3e`, SHA-256은 `59def18b603d5d2a293af279cf2fe2dd3b2634de3c0930bf0cbabf8142ecf64a`다. 이번에는 저장 파일의 두 배열과 모든 요약 통계, 고정 tree의 크기·blob hash를 대조했다.

|---|---|---|---|---|---|---|
| bs_record | 960 × 168 / float64 | 1290240 | 0.000000000 | 30000000.000000000 | 0.007930307540 | 0.000000000000 |
| bs_kge | 960 × 32 / float32 | 122880 | -21.204139709 | 18.954608917 | 0.000000000000 | 0.456803385417 |

두 배열의 161,280개·30,720개 값은 모두 유한하다. 음수는 `bs_kge`의 embedding 성분이며 음수 트래픽이라는 해석은 틀리다. 960개의 물리 cell 또는 MobiGPT의 전체 데이터와 같다고 확정하지 않는다. 두 배열에는 달력 timestamp·물리 station/cell 대응·측정 단위·상류 전처리 명세가 없으며 이 자료로 새 도시의 시간순 예측 성능을 검증한 적은 없다. 길이 168만으로 실제 날짜나 단위를 추정하지 않는다.

검토한 loader는 첫 축의 series를 무작위 순열로 섞어 80%/20%로 나누고, validation 인덱스를 test에도 사용한다. MinMaxScaler는 train series의 모든 시각으로 fit하며 각 sample의 timepoints는 단순 정수 범위다. 이 구현을 독립 미래 시간 구간 평가로 부르지 않는다. `seed` 인수만으로 이 파일 안의 permutation 재현성이 보장되는 것도 아니다. main의 train/evaluate 호출까지 정적으로 읽었지만 전체 모델·utils·수식·README에 연결된 그림은 검토하지 않았고 외부 코드를 실행하지 않았다.

52의 원 실행은 `allow_pickle=False`, 다운로드 1,500,000 bytes·배열 128 MiB·진단 10초 상한을 두었다. 저장된 진단 시간은 0.01390940000055707초다. 다운로드와 파일 쓰기 이후부터 배열 분석까지의 타이머이므로 다운로드·전체 프로세스 지연을 포함하지 않는다. 시작/완료 marker 간격 0.461789초도 별도 값이다. TabICL context·RCTL fit/forward·simple fit은 모두 0으로 기록됐다.

## 54. 질문·입력·실제 수행 범위

질문은 네 곳의 동시 관측과 과거 lag가 있을 때, 관측을 생략한 cell의 현재값을 TabICLv2가 단순 회귀보다 잘 복원하는가였다. 미래값 예측이나 소속 수정 점수 평가가 아니다. 기존 중앙지역 16 grid cell 중 probe는 **3737·3765·6137·6165**, 대상은 **3745·4545·5345·6145**로 고정했다. 대표성이나 실제 기지국 대응을 보장하지 않는다.

Milan H5의 Internet activity 채널 2를 쓴다. H5 전체 shape은 1488 × 10000 × 3이며 이번 대조는 고정 16열과 1488개 timestamp만 읽었다. 각 cell의 처음 672시간 평균으로 해당 cell을 정규화한다. 이 평균은 query보다 앞선 자료로 고정되지만 context 각 행마다 시점별로 다시 추정한 값은 아니다. 단위는 공개 자료의 activity이며 bytes·Mbps가 아니다.

| 구분 | 실제 인덱스와 날짜 | 크기와 의미 |
|---|---|---|
| context | day index 7·9·11·12·14·16·18·20·21·23·25·27·29·30·32·34의 각 첫 16시간 | cell당 256행, 2013-11-08 00:00부터 12-05 15:00 사이의 불연속 16일 |
| query | day index 43·47·51·55의 각 첫 16시간 | 2013-12-14·18·22·26, cell당 64행·전체 256행 |
| 마지막 보고 | 각 query 블록의 직전 시각, index `floor(t/24)*24−1` | 보고 경과 1–16시간; 네 probe는 해당 시각에 계속 관측 가능하다고 가정 |

학습기 세 개는 같은 12열을 받는다: 마지막 보고값, 보고 경과시간, 전날·지난주 해당 시각 값, 동시 probe 네 값, 실제 timestamp의 hour·weekday sin/cos. 네 무학습 기준은 이 정보 중 필요한 일부만 사용한다. 55번의 ‘모든 방법이 같은 입력을 받는다’는 문장은 같은 정보 가용성으로 읽어야 하며, 모든 기준이 12열 전부를 소비한 것은 아니다.

context는 완전히 관측해 둔 과거 자료에서 행별로 생략 상황을 모사했다. 모든 context 시각을 실제 운영상 공동 결측으로 간주하지 않는다. query의 전날·지난주 lag는 네 생략 블록과 겹치지 않는다. 대상의 같은 시각 정답은 입력에 없고 평가에만 쓰이며, 동시 probe 값의 가용성을 전제로 한다. 저장 H5로 정답·정규화·네 기준 예측의 일치를 확인하고 12열 입력을 재구성했다. 다만 **실제로 모델에 전달했던 X 행렬은 따로 저장되지 않아**, 재구성값과 실행 시 X의 바이트 일치를 증명한 것은 아니다.

## 비교 방법과 설정

last_report는 마지막 보고값 유지, day_lag/week_lag는 각각 24/168시간 전 값이다. anchored_day_lag는 `마지막 보고값 + 전날 현재시각 값 − 전날 마지막보고시각 값`이다. 모든 방법은 음수를 0으로 자른다.

Ridge는 StandardScaler와 alpha=1을 사용한다. HGB는 absolute_error, max_iter=100, max_leaf_nodes=15, min_samples_leaf=20, l2_regularization=1, early_stopping=False다. cell당 두 학습기, 총 8 fits로 기록됐다. 이 값만으로 다른 설정의 단순 모델 전체 우열을 확정하지 않는다.

TabICLRegressor v2는 고정 `tabicl-regressor-v2-20260212.ckpt`, ensemble=1, batch_size=1, median, CPU, AMP/FA3/offload=False, n_jobs=1, 자동 다운로드=False다. seed=20260925, torch thread=4·interop=2와 OMP/MKL/OpenBLAS thread=4가 코드에 있다. 각 cell에 context fit 1회·query predict 1회, 총 4 contexts·256행이며 RCTL fit/forward는 0이다. 체크포인트 해시는 settings와 inventory에 맞지만, 당시 모든 라이브러리 버전과 fitted object의 완전 재현은 확보하지 못했다. Tab의 context fit을 gradient 학습 횟수와 동일시하지 않는다.

## 결과: 앞 구간 이득과 후반 손해

정규화 MAE는 4 × 64개 절대오차의 평균이다. cell별·16시간 block별 평균과 두 block씩 묶은 앞/뒤 평균도 저장돼 있다. 원래 activity MAE는 오차에 각 cell의 정규화 평균을 되곱한다. 두 척도의 순위는 다를 수 있으므로 섞지 않는다. 아래 값은 저장 예측을 재계산해 소수 여섯 자리로 표시한 것이다.

계획의 확대 조건은 ① 전체에서 여섯 단순 대안 모두보다 작음, ② 앞·뒤에서 각각 모두보다 작음, ③ 네 cell 중 세 개 이상에서 더 좋은 Ridge/HGB보다 작음의 동시 충족이다. 저장 판정은 **false / false / 0**, 확대 false다. 이 문턱은 탐색 진행 규칙이며 유의성 검정이나 실제 업무 허용오차 기준이 아니다.

## 최초 중단·수정·비용의 연결

수정 전 코드는 context와 query 모두에 공동 결측 lag 충돌 검사를 걸었다. 과거 context에는 서로 겹치는 lag가 있어 모델 호출 전에 assert가 실패하는 경로다. 수정 후에는 query만 검사하며 설명 주석 한 줄도 바뀌었다. 나머지 코드 전체가 동일함을 비교했다. 데이터 선택·seed·모델 설정·확대 기준 변경은 없다.

`preflight_correction.json`은 첫 process exit=1·wall=4.1631648초·새 Tab/RCTL/simple 호출=0·수정 전에 예측을 보지 않았다고 보고한다. 코드의 순서는 실패가 settings/start marker/모델 호출보다 앞선다는 설명을 뒷받침한다. 그러나 **별도 외부 stderr·프로세스 실행 로그는 대조하지 못했으므로**, wall 값과 당시 사람이 결과를 보지 않았다는 보고를 독립 검증으로 표현하지 않는다. 제한된 log 이름 검색에서 일치 항목이 없었으며 전체 원본에 로그가 없다고 결론내리지 않는다.

수정 후 calls 네 항목은 모두 complete이며, result·run_finished·최종 NPZ가 일치한다. partial NPZ의 공유 10개 배열은 최종 파일과 동일하다. 부분 저장을 별도 재현 1회로 세지 않는다. 기록상 실패한 선행 실행과 완료된 모델 실행 한 묶음이며, 기록되지 않은 실행의 부재까지 증명하지는 않는다.

| 비용 항목 | 기록값 | 포함 범위 |
|---|---|---|
| Tab context fit + predict | 2.543409199995949초 | 4 contexts·256 query행 |
| 단순 학습기 fit + predict | 0.4162254999973811초 | Ridge/HGB 8 fits; 아래 cheap에 이미 포함 |
| 수정 후 cheap | 0.7142799000030209초 | stage에서 Tab 시간을 뺀 값 |
| 수정 후 stage | 3.25768909999897초 | H5 로딩·입력 구성·학습/추론·중간 저장·일부 정리 등 |
| 수정 전 실패 process | 4.1631648초 | correction JSON 보고값, cheap에 보수적으로 별도 반영 |
| 호출 사이 RSS 최대 | 480579584 bytes | 연속 측정 peak가 아님 |

stage 시작은 import·파일 hash·settings/start 쓰기 이후다. 종료는 result·최종 NPZ 쓰기와 마지막 hash/완료 marker 전에 잡힌다. Tab 타이머는 fit/predict만, 단순 학습기 타이머는 그 loop만 포함한다. 이 수치를 전체 시스템 지연이나 실제 서비스 memory peak로 쓰지 않는다.

52 직전 원장은 H029 snapshot11과 정확히 같은 바이트다. 52 이후 원장에는 schema 시간 한 항목만 추가됐다. snapshot12 원장은 이어서 54의 Tab 시간·cheap 시간·실패 process를 한 번씩 더한 값과 정확히 일치한다. simple 0.4162255초는 cheap에 포함되므로 다시 더하지 않는다. 현재 원장의 대응 prefix도 같다.

누적 Tab은 49 contexts·35,968행·226.4302954999971초, 남은 count는 31 contexts·24,032행이다. 55의 인쇄값 226.430296초와 저장값에는 마지막 소수 자리 약 0.5마이크로초 차이가 있어 둘을 그대로 보존했다. 저비용 합계는 60.806025800002814초, 기록된 모델링 합계는 1955.243333100001초다. RCTL은 29 fits·추가 0, 상한 초기화 0이다. 초기 전처리·다운로드 등 미계측 시간까지 포함한 전 연구 총비용이 아니며, 옛 남은 예산은 현재 새 실행 권한이 아니다.

## 당시 판단·재사용·재검토 조건

관측 지점 선택 → 생략 이력 복원 → cluster별 RCTL 미래 예측은 처음의 소속 판단과 다른 과제다. 이번 결과로 clustering·RCTL·독립 평가를 통과 처리하지 않았다. 4-cell 비용을 10,000개 cell의 실제 지연으로 단순 선형 환산할 수도 없다. per-cell 복원을 유지한다면 probe를 제외한 각 대상의 context/cache·온라인 추론·관측 갱신 비용을 따로 검토해야 한다.

같은 조건을 재검토하려면 동시 probe의 실제 가용성, 새로운 관측 정책/데이터/기간, 단순 학습기가 놓치는 정보, 미래 RCTL 오차와 연결되는 평가 및 모든 방법의 운영비를 명시해야 한다. 앞쪽 이득만 선택하거나 새 가중치로 이름을 바꾸어 이전 성공으로 기록하지 않는다. 51·53의 센서 선택·복원 선행연구와 55의 신규성 주장은 별도 1차 문헌 검토 후 판단해야 한다.

팀은 보존된 plan·수정 전후 code·settings·calls·result·NPZ·원장으로 먼저 같은 시도를 찾아볼 수 있다. 코드는 원 바이트를 유지한 `.py.txt`이며 실행 안내로 취급하지 않는다. H5·checkpoint·Beijing NPZ는 위치·해시·공식 입수 링크를 연결했지만 바이너리 전체의 팀 접근은 아직 완료되지 않았다. 전체 고유 기록·후속 보고서·비용·접근·최종 원본 변경 및 검색 검수도 계속 남아 있다.

후속 H041의 [STK-Diff 생성 코드 검토](0051-stkdiff-audit.md)는 당시 미검토였던 README 그림4개와 의존 코드·설정647줄을 확인했다. 이 기록의 Beijing 스키마 결과를 재사용하고, 기본 생성과 미래 예측의 차이·단일샘플 CRPS 분모·seed/환경/배치 조건을 추가로 연결했다. H031 당시 읽은 범위와 54의 실제 실험 결과를 소급 변경하지 않는다.
