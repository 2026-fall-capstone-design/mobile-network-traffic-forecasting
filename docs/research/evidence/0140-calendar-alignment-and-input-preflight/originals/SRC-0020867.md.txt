# 111 시각 좌표 보정 후보의 입력 비교 가능성 확인

2026-09-26. 110의 하루 평균 파형 검사가 통과했으므로, 실제 예측 검사에 사용할 입력과 비교 단위를 먼저 고정한다. 이번 실행은 입력 배열과 거리 계산만 수행한다. TabICL·RCTL·Ridge·HGB의 적합 및 예측은 모두 0회이며, 추가 모델 예산도 활성화하지 않는다.

## 자료와 변경 범위

- 기존 16개 cell 전체를 유지한다. `results/pooled_context_101/inputs.npz`의 처음 672개 시점만 사용한다. context는 target 시점 168~671의 504개 sample, query 후보는 672~839이다. 이미 사용한 개발 자료이며 독립 최종 평가로 부르지 않는다.
- 이번 코드는 원본 X와 cell 번호, context_times만 읽는다. query의 실제 target 배열은 읽지 않는다. donor 선택에는 110에서 저장한 앞 21일 평균 profile만 사용한다. 다음 주 profile은 선택에 사용하지 않는다.
- 이동량 delta는 A의 시각 h에 B의 시각 h+delta가 대응한다는 뜻이다. 실제 lag 8개, 하루·일주일 전 값, 평균·표준편차, 요일은 유지하고 hour의 sin/cos 두 열만 바꾼다. 실제 관측 순서나 예측 horizon을 이동하지 않는다.
- 시간축으로 인접한 context와 query 입력이 과거 관측을 공유할 수 있다. 여기서는 query의 정답을 context로 제공하지 않는다. 입력 관측의 공유 자체를 미래 정답 누출이라고 하지 않는다.

## 후보와 query를 고정하는 순서

1. A마다 나머지 15개 cell의 앞 21일 profile에 대해 24개 정수 이동의 제곱차를 비교한다. 110에 저장된 이동별 제곱차를 재사용하며, 반대 방향은 이동 부호를 뒤집어 조회한다. 최소 제곱차가 작은 donor 2개를 고르고 동점은 cell 번호로 정한다. 32개 방향 있는 비교를 만든다.
2. 각 방향의 이동 후보는 0과 제곱차가 가장 작은 비영 이동 2개다. 이동의 동점 순서는 110과 같은 0,+1,-1,...,+11,-11,+12다. profile만으로 정한 최선 이동도 이 셋에 포함된다. 뒤의 예측 오차를 보고 donor나 이동 후보를 추가하지 않는다.
3. 168개 query 위치에서 `floor(linspace(0,167,64))`의 서로 다른 64개 위치를 사용한다. 시간순 앞 32개는 이후 이동량 선택용, 뒤 32개는 선택을 고정한 확인용이다. 각 방향·방법·이동량에 같은 query를 쓴다.
4. donor의 context 504개에서 각 입력 열의 평균과 표준편차를 구한다. 분산이 0인 열의 척도는 1로 둔다. 표준화된 16열의 제곱차 평균의 제곱근을 거리로 사용한다.
5. donor context 안에서 각 sample의 앞뒤 8시간을 이웃 후보에서 제외하고, 다섯 번째 가까운 이웃의 거리를 구한다. 그 504개 거리의 95백분위수를 고정 반경으로 쓴다. query는 donor context의 다섯 번째 이웃까지 거리가 이 반경 안인지 판정한다.
6. 세 이동 조건 모두에서 반경을 만족하는 query의 교집합만 후속 예측 비교에 사용한다. 같은 정답 문제를 유지하기 위한 조건이다. 이 기하학적 필터를 실제 조건부 분포의 공통 지원을 증명하는 방법으로 해석하지 않는다.

## 실행 전 정한 통과 조건

한 방향에서 앞 32개와 뒤 32개 중 각각 16개 이상이 남아야 한다. 그러한 방향이 8개 이상, 대상 A가 8개 이상이면 후속 소규모 예측 비교를 구체화할 자료가 있다고 판단한다. 이는 모형 실행을 위한 자료 충분성 기준이며 효과 검정이나 신규성의 기준이 아니다. 모자라면 반경을 늘리거나 donor 수를 추가하여 억지로 통과시키지 않는다. 제외된 방향과 query 수를 모두 보존한다.

다음 예측 검사를 실행한다면 같은 context·query·이동 후보에서 TabICLv2, StandardScaler+Ridge(alpha=1), 기존 101과 같은 HGB를 비교한다. 각 방법은 앞 절반의 실제값으로 이동량 하나를 선택하고 뒤 절반에서 그 선택을 고정한다. profile만으로 정한 이동량과 무이동도 같은 뒤 절반에서 비교한다. TabICL이 다른 선택이나 유용한 개선을 만들었는지, 두 단순 회귀도 같은 효과를 냈는지를 구별한다. 실제 실행 설정과 판정 기준은 별도 계획에서 확정한다.

## 비용과 보존

- 16개 donor의 504×504 거리, 방향 32개×이동 3개×query 64개×context 504개의 거리만 계산한다. 시간 상한 30초, RSS 상한 1GiB, CPU thread 4개 이내다.
- 설정·코드·입력·원장 hash를 고정한 뒤 한 번 실행한다. query 원위치, 세 이동 입력, 반경, mask, 후보 목록을 저장하여 후속 단계가 다시 추출하지 않게 한다.
- 후속 TabICL 요청의 실제 context 수와 query 행 상한도 mask를 기준으로 산술 계산한다. 이번에는 모델 예산을 예약하거나 소비하지 않는다.
- 원장에 실제 배열 계산 시간만 한 번 추가하며 기존 사용량·상한·추가 회차의 잔여 9회 적합을 보존한다. 결과가 좋더라도 cluster 소속이나 RCTL 설정은 아직 정하지 않는다.
