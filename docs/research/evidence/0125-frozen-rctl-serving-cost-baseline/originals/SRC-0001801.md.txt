# 95. 같은 예측을 유지하는 묶음 처리와 clustering의 계산 비용

2026-09-26. `95_serving_cost_plan.md`를 먼저 고정한 뒤 저장된9개 RCTL checkpoint로 한 번 실행했다. 추가 학습·TabICLv2 추론·새 소속 선택은 없었다.

## 이번에 확정한 것

**기존 cell별 scalar RCTL에서는 cluster 수를 줄여도 예측할 cell 행은 그대로다.** 같은 모델을 쓰는 행을 한 번에 넣으면 실행 overhead를 줄일 수 있지만, 여러 cell을 하나의 대표 예측으로 바꾸는 것은 아니다. 이 차이를 실제 CPU 실행으로 확인했다. 앞으로 비용 비교에서 cell을 한 개씩 호출하는 구현을 기본 대안으로 사용하지 않는다.

이것은 TabICLv2 기반 clustering의 신규성이 아니다. 기본 구현을 바로잡아 얻는 효율을 연구 알고리즘의 효과로 세지 않도록 하는 결과다. 이미 실패한 B2의 성능 판정을 바꾸지 않는다.

## 1. 실제 비교한 조건

기존16cell·8시점×9입력·seed20260925의 global1개, Tab risk4개, empirical risk4개 checkpoint를 사용했다. 모든 가중치와 BatchNorm buffer를 고정하고 평가 모드로 실행했다. 입력은 기존 개발 구간840..1007에서 사전에 고른12시점이다. 새로운 미래 구간이나 별도 성능 검증이 아니다.

한 시점의16cell을 예측할 때 각 방법을 두 방식으로 실행했다.

- **cell별 호출:** 각 cell의8×9 입력을1행씩 넣어 총16번 호출한다.
- **묶음 호출:** 같은 RCTL을 사용하는 cell을 batch로 넣는다. global은16행을1번, K4는4행을4번 처리한다.

같은 시각에 이미 관측된 입력만 묶었다. 여러 미래 시점의 자료가 도착할 때까지 기다려 batch를 키우는 방식은 아니다. Torch CPU4 intra-op/2 inter-op threads, float32다. 입력 준비와 checkpoint 로딩을 제외하고 모델 실행과 결과를 원래 cell 순서로 모으는 시간을 쟀다. 온라인 전체 지연이나 GPU 성능을 측정한 것은 아니다.

## 2. 측정 결과

각 경로의2회 warm-up 뒤12시점×3반복을 측정했다. 표는 한 시점의16cell을 모두 처리한 시간이다.

| 보존된 모델 | cell별 호출 중앙값 | 묶음 호출 중앙값 | 묶음 호출 P10–P90 | cell별/묶음 시간비 |
|---|---:|---:|---:|---:|
| global, K1 | 33.186ms | 3.493ms | 3.337–5.506ms | 9.501 |
| 기존 Tab risk, K4 | 33.865ms | 14.005ms | 12.236–15.399ms | 2.418 |
| empirical risk, K4 | 34.038ms | 14.152ms | 12.614–14.757ms | 2.405 |

P10–P90은36개 timing의 관측 분위수다. 독립 반복에 대한 신뢰구간이나 유의성 검정이 아니다. 경로 실행 순서는 반복·시점별로 순환시켰다. 현재 장비의 작은 benchmark이며16cell 결과를10000cell의 지연시간으로 선형 확대하지 않는다.

동일 방법에서 두 호출 방식의 최대 예측 차이는 global7.15×10⁻⁷, Tab risk1.19×10⁻⁶, empirical risk1.07×10⁻⁶이었다. 모두 사전에 정한2×10⁻⁵ 이내다. 원 checkpoint·입력 파일·모델 상태는 실행 전후 같았다. 정확도를 바꾸는 새로운 학습으로 속도를 얻은 결과가 아니다.

## 3. 모델 개수·예측 행·메모리의 차이

| 비교 항목 | global K1 | 기존 K4 |
|---|---:|---:|
| 시점당 예측 행 | 16 | 16 |
| 묶음 처리 시 모델 호출 | 1 | 4 |
| parameter·buffer 상태 tensor | 701,412bytes | 2,805,648bytes |
| checkpoint 파일 합계 | 745,123bytes | 2,980,492bytes |

모든 모델의 구조가 같아 상태 tensor 저장량은 K4가 정확히4배다. 그러나 프로세스 전체 메모리가4배라는 뜻은 아니다. 이번 프로세스에는9개 모델과 Torch runtime이 함께 있었으며 관측한 최대 RSS는233,689,088bytes였다. 이는 주기적인 완전한 메모리 추적값도, 방법별 독립 peak도 아니다.

평가 모드에서는 각 행의 convolution·LSTM·선형층 계산은 여전히 필요하다. batch를 크게 하면 라이브러리와 하드웨어가 이를 효율적으로 처리한다. 호출1번이 예측 문제1개를 의미하지 않는 이유다. 따라서 비용 설명은 다음을 따로 제시해야 한다.

1. 저장하는 서로 다른 RCTL 가중치 수.
2. 실제로 처리하는 입력 행과 원소 수.
3. 호출·batch 구성 및 측정된 실행 시간.
4. clustering을 준비하는 TabICLv2의 context·query 비용.

## 4. 연구 설계에 반영하는 판단

원래 목적의 ‘RCTL 수 감소’에는 저장량과 묶음 처리의 이점이 있을 수 있다. 다만 이를 전체 연산이 같은 비율로 줄어드는 것으로 쓰지 않는다. 현재 결과에서 global 묶음 처리와 K4 묶음 처리의 시간 차이는 분명하지만, 같은K4의 Tab risk와 empirical risk는 구조상 같은 수의 행·모델·호출을 사용한다. 약0.147ms의 중앙값 차이를 Tab clustering의 유의미한 속도 우위라고 해석하지 않는다.

동일 checkpoint의 이전 전체 평가 기록에서는 global의 평균 오차가 두K4 대안보다 작았다. 이번 timing은 그 오차를 새 구간에서 재검증한 것이 아니다. 두 기록을 함께 보면, 현재 B2에 대해 ‘더 많은 모델이지만 계산을 줄인다’는 별도 이점은 확보되지 않았다. 모든 다른 partition이나 모델 학습 방법의 가능성을 배제하는 결과는 아니다.

신규성이 있는 비용 개선을 주장하려면 이 묶음 처리 기준에 비해 실제로 생략하는 일을 특정해야 한다. 대표 예측·다중 출력·출력 압축은 이미48–50·74·81에서 검토했고, 단순히 이름을 바꾸어 다시 제안하지 않는다. 더 적은 호출 자체는 새로운 예측 정보도, Tab의 역할도 아니다.

이번 결과로 **향후 비교의 기본 실행 방식은 같은 가중치를 쓰는 cell의 동시 batch 처리**로 확정한다. 이는 기초 구현 조건이며 추천 연구 방향을 새로 채택한 것은 아니다. 남은 핵심은 이 기준에서도 가치가 있는 정확도·모델 수·실제 계산의 개선을 특정하는 일이다.
