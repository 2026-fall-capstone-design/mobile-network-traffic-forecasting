# RCTL 모델 수와 실제 예측 비용의 차이

**같은 모델을 사용하는 cell을 한 번에 처리하는 것만으로도 예측 시간이 크게 줄었습니다. 이 효과는 TabICLv2의 기여와 구분해야 합니다.** 앞으로 제안 알고리즘의 계산 효율은 이 묶음 처리 방식을 기준으로 비교하겠습니다.

2026-09-26, 이미 학습해 둔 RCTL을 사용해16개 cell의 같은 시각 입력을 예측했습니다. 추가 학습은 하지 않았습니다. 현재 CPU에서 입력 준비·모델 로딩을 제외한 실행 시간의 중앙값은 다음과 같습니다.

| 보존된 예측 모델 | cell을 하나씩 처리 | 같은 모델의 cell을 묶어 처리 |
|---|---:|---:|
| global RCTL1개 | 33.19ms | **3.49ms** |
| 기존 TabICLv2 기준으로 나눈 RCTL4개 | 33.86ms | **14.01ms** |
| 실제값 기준으로 나눈 RCTL4개 | 34.04ms | **14.15ms** |

각 방식은12시점에 대해3회 반복했습니다. 동일 모델의 두 처리 방식에서 예측값의 최대 차이는 약0.0000012로, 사전에 정한 수치 허용 범위 안이었습니다. 가중치와 BatchNorm 상태도 바뀌지 않았습니다. 이는 새로운 정확도 비교가 아니라 실행 방식의 비교입니다.

## 무엇이 줄고, 무엇이 그대로인가

global 모델은16개 입력 행을 한 번에 처리합니다.4개 cluster에서는 각 모델이 자신의4개 행을 처리합니다. **두 경우 모두 총16개 cell을 예측합니다.** 모델 호출이 줄어드는 것과 예측할 데이터가 줄어드는 것은 다릅니다.

반면 저장해야 하는 모델 상태는1개일 때701,412bytes,4개일 때2,805,648bytes였습니다. 모델 수 감소는 이 저장량을 직접 줄입니다. 라이브러리·입출력 buffer 등이 포함되는 전체 프로세스 메모리와는 구분해야 합니다.

## 연구 방향에 반영할 내용

- 느린 cell별 호출을 비교 대상으로 삼으면, 기본적인 batch 처리의 이득을 제안 알고리즘의 성과로 잘못 설명할 수 있습니다. 같은 가중치를 사용하는 cell은 묶어서 처리하는 조건을 기본으로 두겠습니다.
- cluster 수, 예측하는 행 수, 호출 횟수, 실제 실행 시간, TabICLv2의 사전 계산 비용을 각각 제시해야 합니다.
- 같은4개 cluster에서 측정한 두 방법의 작은 시간 차이는 TabICLv2의 속도 우위로 해석하지 않겠습니다. 처리 구조와 데이터량이 같고, 소규모 timing만 확인했기 때문입니다.
- 현재보다 의미 있는 계산 개선을 제안하려면 이 빠른 기본 구현에서도 어떤 연산을 생략할 수 있는지 보여야 합니다. 대표 예측이나 다중 출력이라는 이름만 추가해서는 그 근거가 되지 않습니다.

이번 확인에는 약5.45초가 들었고 RCTL을 새로 학습하거나 TabICLv2를 추가 호출하지 않았습니다. 현재 장비의16cell 결과이므로 대규모 서비스의 지연시간으로 그대로 확대하지 않습니다. 새 연구 방향과 최종 Word는 아직 미완료입니다.
