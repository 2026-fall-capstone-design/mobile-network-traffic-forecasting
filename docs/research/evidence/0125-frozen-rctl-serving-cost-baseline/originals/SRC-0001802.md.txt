# 95. 고정 RCTL의 모델 수·묶음 처리·예측 비용 구분

2026-09-26. 실행 전 고정 계획이다. 94는 최신 원문과 정보 가용성의 차이를 확인해 지연 보정안을 추가하지 않도록 판단을 바꾼 progress다. 현재 snapshot36, 누적 비용 원장, 48–50·74·81·87·93의 검토 범위를 다시 확인했다.

## 확인할 주장 하나

기존 cell별 scalar RCTL에서 cell들을 같은 cluster에 넣는 것은 예측할 행을 줄이는가, 아니면 가중치 저장량과 한 번에 처리할 수 있는 묶음을 바꾸는가? 보존된 모델을 실행해, 같은 예측을 cell별 호출과 cluster별 묶음 호출로 수행할 때 실제 CPU 예측 시간과 상태 저장량을 구분한다.

대표값 예측·출력 압축·다중 출력 학습은 이미 검토했으므로 다시 실행하지 않는다. 이번 측정은 새로운 clustering 후보의 성공 실험이 아니다. RCTL 출력·손실·측정 시간을 사용해 cell 소속이나 후보 임계값을 바꾸지 않는다.

## 고정 자료와 비교

- 보존된 `results/rctl_pilot/frozen_settings.json`의 seed20260925 모델 중 global1개, tabicl_risk4개, empirical_risk4개를 그대로 사용한다. 총9개 checkpoint다. 선택은 대표 구조와 기존 주 비교를 대조하기 위한 것이며 좋은 latency 결과를 보고 고르지 않는다.
- `results/design_data.npz`에서 기존16cell의 시각840..1007 중 `linspace(840,1007,12,dtype=int)`로 정한12시점의 입력을 사용한다. 입력은 원래의8×9이고 query의 실제값을 예측 입력에 넣지 않는다. 이미 관찰한 개발 구간이다.
- 각 방법에서 (1) cell당1행씩16번 호출, (2) 같은 가중치를 쓰는 cell을 묶어 global은16행1번, K4는4행씩4번 호출한다. 총6가지 경로다. 여러 미래 시점의 입력을 한꺼번에 넣어 온라인 latency를 유리하게 만들지 않는다.
- 4 CPU intra-op threads,2 inter-op threads, float32, `eval()`과 `torch.inference_mode()`, 기존 Torch port 그대로다. GPU·compile·quantization·streaming hidden-state 변경은 없다. 학습·optimizer·gradient·BatchNorm 갱신0.
- 입력 텐서는 미리 구성한다. 한 시점의16cell을 예측하고 결과를 원래 cell 순서에 모으는 시간만 측정한다. 전처리·모델 로딩 시간은 별도로 보고하고 온라인 전체 지연이라고 부르지 않는다.

## 횟수와 확인

각 경로의 첫2시점으로2회 warm-up 후,12시점×3반복을 실행한다. 반복·시점마다 경로 순서를 순환시켜 항상 같은 경로가 먼저 실행되지 않게 한다. 각 경로는36개의 시점별 timing을 가진다. median·10/90percentile 및 반복별 median을 보고한다. 기기 한 대의 소규모 timing이며 통계적 유의성·다른 하드웨어의 속도를 주장하지 않는다.

같은 방법의 cell별 경로와 묶음 경로의 예측 차이를 최대 절대값2e−5 이내로 확인한다. 학습 가중치와 모든 buffer 및 원 checkpoint hash가 실행 전후 같은지 확인한다. 이전 checkpoint 검증의 허용 오차를 사용한 수치 일관성 검사이며 연구 효과 합격선이 아니다.

가중치·buffer의 실제 tensor bytes와 checkpoint 파일 bytes를 각각 센다. 프로세스 RSS는 Torch runtime과9개 모델이 함께 차지하는 값이므로 K1·K4의 순수 모델 메모리비로 해석하지 않는다. 입력·출력 원소 수와 호출 수·행 수도 기록한다.

## 결과별 행동

- 묶음 호출이 같은 예측으로 빨라지면 모든 향후 비교의 기본 구현으로 둔다. 이를 TabICLv2의 연구 신규성으로 세지 않는다.
- K를 줄여도 시점당16행을 처리한다면 모델 수 감소를 같은 비율의 연산 감소로 표현하지 않는다. checkpoint 저장량·호출 overhead·행당 core 계산을 구분한다.
- 새 Tab 기반 구성의 절감 주장은 이 묶음 처리 기준보다 실제로 어떤 연산을 제거하는지 제시해야 한다. 현재 임의의 추가 architecture를 권고하지 않는다.
- 예측이 일치하지 않으면 BatchNorm 모드·입력 배치·수치 경로를 조사한다. 성능 차이로 해석하거나 model을 재학습하지 않는다.
