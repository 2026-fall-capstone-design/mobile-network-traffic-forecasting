# 목표

네트워크 트래픽 예측에서 TabICLv2로 해결할 가치가 있는 문제를 다시 찾고, 가장 가까운 선행연구보다 무엇을 어떤 원리로 개선하는지 설명할 수 있는 연구 방향 하나를 구체적으로 설계하라.

기존 cell을 clustering한 뒤 cluster별 RCTL로 예측하는 구조를 유지한다. 기존의 sample 교체 검사, 공통 context 병합 검사, 예측 허용 구간은 유지해야 할 조건이 아니다. 해결할 문제에 맞지 않으면 폐기하고 다시 설계하라.

이번 목표는 현재안을 평가하고 중단을 권고하는 것으로 끝나지 않는다. 한 후보의 근거가 부족하면 그 후보를 버리거나 수정하고, 다른 문제 또는 다른 원리의 후보를 계속 탐색하라. 최소 하나의 방향에 대해 문제의 중요성, 선행연구 대비 차이, 개선 원리, TabICLv2의 역할, 구현 가능성, 작은 확인 결과 또는 그에 준하는 직접 근거를 연결할 때까지 설계를 계속하라.

단, 계속 탐색하라는 요구를 신규성이나 성능 향상을 만들어내라는 뜻으로 해석하지 마라. 본 실험 전에도 판단할 수 있는 설계의 타당성과 본 실험에서만 확인할 수 있는 일반적인 성능 향상을 구분한다. 전체 성능의 보장은 완료 조건이 아니지만, 핵심 원리의 확인을 전부 본 실험으로 미룬 제안도 완료로 인정하지 않는다.

## 0. 현재 목표와 재개 시 수행할 작업

이 파일은 지속적으로 수행할 연구의 기준이다. 실행할 때마다 새로 작성하거나 사용자에게 다시 제시할 산출물이 아니다. 다음 미완료 작업은 `tmp/redesign_20260925/research_state.json`의 `next_action`에서 읽는다. 이미 처리한 질문은 같은 파일의 `resolved_requests`로 구분한다. 자동 재개에서 대화 이력의 마지막 일반 질문을 다시 답하지 않는다. 사용자가 새로 질문하면 그 요청을 우선 처리하고 필요한 변경을 연구 상태에 반영한다.

2026-09-28 현재 자동 연구는 `Tab-ICL 논문 조사` 채팅의 native goal이 수행한다. 사용자가 `tabiclv2` 예약 작업을 삭제했으므로 과거 heartbeat 운영 지침은 현재 실행 기준으로 사용하지 않는다. 앱에 등록된 목표가 참조하는 이 파일의 제0.2·9.1·9.2·12절을 현행 판단·예산·진행 규칙으로 적용한다. 등록된 목표나 압축 요약에 남은 과거 중복 방지 문구로 goal 자신의 연구를 건너뛰지 않는다. 등록 본문에 남은 ‘잔여 예산이 없는 종류의 실행은 시작하지 않는다’는 문구는 제9.1절의 필요한 증액·예약을 완료하기 전에는 실행하지 않는다는 뜻으로 적용하며, 계획에 근거한 자율 증액을 금지하는 조건으로 사용하지 않는다. 이 참조 문서의 개정과 앱에 저장된 goal 본문 자체의 변경은 구분하여 기록한다.

연구의 중심은 **UPC가 정하던 cell 소속을, TabICLv2가 제공하는 유용한 정보로 개선하는 것**이다. RCTL은 소속을 고정한 뒤 효용을 확인하는 최종 예측기로 둔다. 특정 Tab 점수와 RCTL 결과의 불일치는 그 점수의 해석을 제한하는 근거이며, 모든 독립적 clustering의 불가능성을 뜻하지 않는다. 두 모델의 모든 불일치 원인을 먼저 설명해야 후보를 설계할 수 있다는 관문을 만들지 않는다. 원인 분석을 추가할 때는 결과에 따라 바꿀 소속 결정 또는 후보 채택 판단을 먼저 적는다.

사용자는 clustering → RCTL을 유지한다고 다시 확정했으며, 아래 후보 생성 절차를 현재 목표에 반영하여 연구를 계속 진행하도록 요청했다. 최종 예측기를 TabICLv2로 교체하는 방향으로 우회하지 않는다. 기존 sample 교체·공통 context 절차를 되살리는 것 역시 의무가 아니다.

다음 탐색의 주목표는 **같은 실제 RCTL 모델 수에서 UPC와 강한 단순 clustering보다 미래 예측 오차를 줄이는 것**이다. clustering 계산 비용은 별도 제한 조건으로 기록한다. Global RCTL은 분할의 실용적 필요성을 확인하는 비교군으로 유지하되, K가 다른 비교를 동일 K의 효과와 섞지 않는다. 기존 K4 실패를 피하려고 결과를 본 뒤 목표 지표·cell·시점을 바꾸지 않는다. 다른 K를 확인하려면 원 논문 또는 사용 조건의 근거와 사전 계획을 명시한다.

매 회차의 순서는 다음과 같다.

1. 기존 결과와 원 논문에서 비교 조건이 같은 부분·다른 부분을 분리한다. 이미 끝난 분석과 원문 읽기는 재사용한다.
2. 실제 손해를 `잘못 합친 손해`, `불필요하게 나눈 손해`, `현재 자료로 원인을 구별할 수 없음`으로 나누어 살핀다. 설명이 가능한 현상과 원인이 확인된 현상을 구별한다.
3. 관측 근거가 있는 오류 하나를 선택한다. 오류의 발생 빈도·영향과 가장 강한 단순 해결책을 정한다. 이후 값의 차이 또는 학습/검증 gap만으로 원인을 확정하지 않는다.
4. 그 오류를 바꾸는 후보 명세 한 개를 먼저 완성한다. 핵심은 `기존 방법이 왜 오판하는가 → TabICLv2가 무엇을 추정하는가 → 어떤 소속 결정이 달라지는가 → 실제 RCTL 학습 자료가 어떻게 바뀌는가`이다.
5. 가장 가까운 원문·공식 코드와 비교하여 기존 규칙과의 동등성, 적용 가정, 추가 비용을 확인한다. 문헌상 차이가 없는 안은 모델 이름만 바꾸어 추천하지 않는다.
6. 명세와 작은 확인 계획을 고정한 뒤, 필요한 최소 실행 예산을 편성하고 수행한다. 결과에 따라 후보를 수정·기각·진행하며 다음의 구체적 행동을 기록한다.

후보를 제출하기 전에 그 후보의 성공 결과가 이미 있어야 한다고 요구하지 않는다. 실제 문제, 개선 원리, 실패 가능한 예측, 비교 방법과 실행 가능성이 있으면 작은 확인으로 진입할 수 있다. 반면 최종 추천에는 제11절의 직접 근거가 필요하다.

### 0.1. 기존 기록을 연결하고 현재 집중할 문제를 유지한다

2026-09-28 사용자 요청에 따른 보완이다. 이 절차는 이후 기록과 과거 근거의 재사용에 함께 적용한다. 과거 문서에 새 양식이 없다는 이유로 결과를 무효화하거나 모두 다시 작성하지 않는다. 이 보완의 상태는 `tmp/redesign_20260925/research_focus.md`에 기록한다. 문서 수정과 목록 생성만으로 초기 근거 검토나 연구 진전이 완료됐다고 표시하지 않는다.

**초기 통합 검토는 한 번 수행하고 이후에는 변경분을 반영한다.** 실행 중 작업이 있으면 실제 결과·실행 표시·정산부터 확인하고, 최신 연구 단계에서 통합 검토를 이어간다. 특정 과거 단계로 되돌리거나 현재 완료 결과를 버리지 않는다.

1. 번호가 붙은 연구 문서와 최종·중간 보고서의 목록을 후보 인덱스 및 진행 기록과 대조한다. 계획·실제 실험·논리/문헌 분석·실행 실패·운영 수정의 종류, 연결된 기록, 검토하지 않은 범위를 구분한다. 파일명·제목으로 추정한 종류는 내용 확인 전까지 확정하지 않는다. 목록은 `maintenance_research_focus_20260928/history_inventory.json`을 출발점으로 쓰되 생성 시점 이후 자료를 보완한다. 백업·snapshot의 중복 사본을 새 연구로 세지 않는다.
2. 인덱스와 진행 기록을 전체 범위에서 살펴 같은 관측 문제를 다룬 기록을 묶는다. 문제별로 관측 사실·조건·영향, 해석/원인 가설, 시도한 판단 규칙, 단순 대안, 실제 결과, 미해결 연결과 상세 근거를 정리한다. 누락·모순은 원문 기록으로 돌아가 확인한다. 기간·cell·K·입력·context·평가기·개발/독립 평가가 다른 결과를 같은 조건의 증거로 합치지 않는다.
3. 현재 문제의 선택이나 후보 배제를 좌우하는 결과와 반례를 우선 상세 검토한다. 실제 실험의 부정적 결과, 특정 가정의 논리 반례, 문헌상 중복, 당시 자원/구현 제약, 단순 미확인을 구별한다. 재개가 필요한 후보는 바뀐 조건 또는 새 근거를 적고 이전 결과를 재사용한다. 원래 기록은 보존하고 정정은 근거와 적용 범위를 가진 후속 기록으로 남긴다. 모든 논문 재독과 모델 재실행은 기본 절차가 아니다.
4. 문제의 관측 근거, 손해의 중요성, 강한 단순 대안 이후에도 남는 질문, 작은 확인으로 판단을 바꿀 가능성을 비교해 현재 문제 하나를 정한다. 새 문서 번호나 새 논문이라는 이유로 우선하지 않는다. 아직 선택 근거가 부족하면 상태를 `선정 중`으로 두고, 다음 행동을 선택을 가를 구체적인 확인으로 정한다. 모든 원인과 과거 문서를 완전히 해명해야만 다음 확인을 할 수 있다는 관문은 만들지 않는다. 선택에 영향을 줄 미검토 기록은 명시하고 해당 결론을 잠정으로 둔다.

집중 문제 기록에는 다음을 담는다. 별도 장문 보고서 대신 기존 상세 기록을 연결하고 바뀐 판단을 적는다.

- 문제 ID·상태·선정/변경 이유와 적용한 검토 범위.
- 관측 사실과 근거 위치, 비교 조건·손해·적용 한계. 확인된 사실과 아직 모르는 원인을 분리한다.
- 구분할 원인 가설과 가설별로 달라질 소속 결정. 원인이 미확인이어도 진단 가능한 가설을 기록할 수 있다.
- TabICLv2가 제공할 정보, 가장 강한 단순 대안, 실제 cluster 구성과 RCTL에 전달할 자료의 변화.
- 현재 논문 조사·분석·설계가 해결할 질문, 성공·실패·혼재 결과에서 달라질 판단.
- 재사용할 결과, 최소 확인의 자료·비교·시간 경계·비용·기각 조건, 다음 계획의 위치.

각 행동은 문제 ID와 미해결 질문에 연결한다. 문제 선정 중의 문헌 탐색도 허용하되 어떤 문제의 존재·원인·실행 가능성을 확인하는지 적는다. 논문의 유용한 정보가 현재 문제와 연결되지 않으면 참고 근거로 보존하고, 새로운 중심 문제로 바꾸는 이유를 기록한다. 초기 검토의 처리 범위와 남은 확인을 이어받아 같은 목록 정리를 매 회차 반복하지 않는다.

**작은 검증으로의 전환:** 확인할 주장, 같은 정보를 쓰는 비교군, 실행 가능한 명세와 비용, 결과별 진행·수정·기각 판단이 갖춰지면 기존 제9.1절에 따라 필요한 작은 확인을 수행한다. 추가 조사는 이 중 아직 정하지 못한 부분을 해결하는 데 사용한다. 원인의 완전한 증명, 성능 향상의 사전 입증, 모든 구성 요소의 독창성을 실행 전 조건으로 요구하지 않는다. 소규모 원인 진단과 최종 추천의 증거 수준을 구분한다.

**문제의 유지와 전환:** 단순 대안으로 손해가 해소됨, 영향이 중요하지 않음, 현재 조건에서는 가설을 구별할 수 없음, 더 강한 관측 근거의 발견 등으로 초점을 바꿀 수 있다. 이전 문제의 남은 질문·전환 근거·다시 열 조건을 남긴다. 한 방법의 실패를 문제 전체의 소멸로 해석하거나 새 방법을 발견한 것만으로 초점을 바꾸지 않는다. 272의 앞/뒤 구간 차이는 검토할 관측 중 하나이며, 그 원인을 시간 변화·선택 오차·학습 부족으로 미리 확정하지 않는다. Tab과 kernel의 같은 소속은 잘못된 소속의 정답 label이 아니다.

연구 채팅이 최신 기록을 확인한 뒤 `research_state.json`에 `active_problem`으로 이 집중 기록의 상대 경로·문제 ID·상태를 연결하고, `next_action`에는 그 문제의 미해결 질문과 결과별 판단을 반영한다. 사실과 상세 계획은 집중 기록 및 기존 계획에 두고 여러 파일에 중복 복사하지 않는다. 점검 채팅은 연구 채팅이 갱신 중인 `next_action`·실행 표시·결과·원장을 덮어쓰지 않는다. 새로운 보완을 실제로 읽고 반영한 시점과 작업을 연구 채팅이 집중 기록 및 진행 기록에 한 번 남긴다. 초기 안내의 단계 번호보다 적용 당시 최신 상태가 우선한다.

### 0.2. 관측 문제별 판단 지점과 검증으로의 전환

2026-10-02 사용자는 ‘완료된 비교 정리 → 남은 관측 문제 선택 → 후보 하나의 명세 → 소속을 고정한 RCTL 확인 → 결과별 진행·전환’ 계획을 파일에 적용하도록 요청했다. 이 절은 매 회차의 별도 보고서나 모든 원인에 대한 추가 증명 의무가 아니다. 제0.1절의 집중 기록에 판단이 바뀐 근거만 연결한다.

**판단 시점:** 핵심 비교가 완료되었을 때, 현재 방법의 핵심 가정이 기각되었을 때, 강한 단순 대안이 관측한 손해를 해소했을 때, 제한된 진단이 끝났을 때 또는 조건 변경으로 기존 판단을 유지할 수 없을 때 적용한다. 진행 중인 한정 실행은 실제 완료 출력·검수·정산부터 확인하며, 완료된 확인을 다시 실행하지 않는다. 초기 이력 통합이나 현재 지침의 적용 설명을 매번 반복하지 않는다.

**문제별로 정리할 내용:** 관측 사실과 조건·손해, 종료한 방법, 완료된 확인, 강한 단순 대안 이후에도 남는 질문, Tab이 바꿀 결정, RCTL에 전달할 실제 자료, 다음 판단을 바꿀 최소 확인을 한 번에 정리한다. 실제 부정 결과, 문헌상 중복, 논리 반례, 구현·학습 실패, 미확인은 별도로 표시한다. 개별 방법의 실패를 문제 전체의 소멸로, 고정 대비의 이익을 소속 검색 알고리즘의 성공으로 확대하지 않는다.

| 현재 판단 | 다음 행동 |
|---|---|
| 반박 가능한 가설·고정 가능한 규칙·동일 정보 비교군·비용·결과별 판단이 갖춰짐 | 후보 하나를 명세하고 필요한 작은 검증에 들어간다. 모든 원인 규명이나 최종 신규성의 사전 입증을 추가 관문으로 붙이지 않는다. |
| 필요한 정보 하나가 아직 없음 | 그 정보가 바꿀 결정과 결과별 행동을 적고 필요한 원문·코드·제한 진단만 수행한다. 끝나면 이 판단 지점으로 돌아온다. |
| 새 알고리즘은 미정이나 유용성 판단을 바꿀 고정 소속이 있음 | 제9.2절의 실제 RCTL 연결 진단을 우선 검토한다. 이를 Tab 고유 알고리즘의 성과로 제출하지 않는다. |
| 단순 대안으로 손해가 해소되거나 중요한 잔여 문제·구별 가능한 가설이 없음 | 종료 범위·남은 질문·다시 열 조건을 남기고 근거가 있는 다른 관측 문제로 전환한다. |
| 실행·검수·학습 실패로 판단하지 못함 | 실제 출력과 실패 비용을 보존하고 필요한 복구만 수행한다. 미실행이나 학습 실패를 성능 기각으로 표시하지 않는다. |

**추가 조사·진단의 계약:** 미해결 질문 하나, 답에 따라 바뀔 소속 규칙 또는 후보 판단, 재사용할 근거와 필요한 추가 확인, 확인 종료 후 진행·기각·전환 조건을 먼저 적는다. 논문은 추정 대상·사용 정보·시간 처리·소속 결정식·비용·적용 가정 중 무엇을 바꾸는지 연결한다. ‘Tab과 RCTL의 모든 불일치 원인’을 한 번에 규명하려 하지 않는다. 질문을 해결했는데도 후보를 실행하지 않고 다음 진단·비교기·보정 모듈을 자동으로 붙이지 않는다. 추가 확인이 필요하면 새로 밝혀진 어떤 정보가 실제 결정을 바꾸는지 다시 적는다.

**현재 관측에 대한 적용:** 494의 고정480행 보정 경로는 미채택이며, 497은 원래 전체 native 고정 교환을 완료했다. 각 예측기 내부의 교환 전후 오차 변화로 해석하고 모델 간 우열·최종 군집 개선·신규성으로 대신하지 않는다. 같은 선택을 한다고 모든 추정 정보가 같다는 결론도 내리지 않는다. 유용한 소속 판단과 실제 비용 병목이 확인되기 전에는 context 축소를 보조 문제로 둔다. 이 방법의 기각을 모든 context 축소의 불가능성으로 확대하지 않는다.

적용 시점에 498 등 현재의 한정 비교가 이미 진행·완료됐으면 그 결과를 먼저 재사용한다. 같은 정보의 대안이 고정 교환과 시간별 방향을 재현하는지 확인한 뒤, ‘하루 profile 이후에도 남는 자료 공유 차이가 실제 RCTL에 유용한가’와 ‘Tab이 추가하는 정보·결정·효율이 무엇인가’를 분리해 판단한다. 앞 질문의 작은 확인을 뒤 질문의 완전한 해명까지 미루지 않는다. 다른 관측 문제로 전환할 경우에도 현재의 고정 소속에 대한 연결 확인이 왜 판단을 바꾸지 못하는지 범위와 근거를 남긴다.

연구 채팅은 실제 적용 시점의 최신 결과를 기준으로 research_focus.md에 판단을 남기고, research_state.json의 active_problem·next_action, 후보 인덱스와 progress.md를 연결한다. 다음 행동 하나에는 확인 대상·작업·비용·결과별 결정을 적는다. 부정적 결론으로 개별 문제를 닫는 것, 지침 적용, 연결 진단 완료, 제11절의 전체 goal 완료는 서로 구분한다. 점검 채팅의 수정은 새 실험이나 후보 채택으로 세지 않는다.

최신 판단 보고서도 재검토 가능한 자료다. 확인된 반례와 실행 기록은 재사용하되, 보고서의 해석을 원문의 사실이나 수학적 정리와 동일하게 취급하지 마라. 초기 preflight의 수치 예시와 이후 redesign에서 실제 실행한 TabICLv2·RCTL 확인을 구별한다. 과거의 '실제 모델 미실행' 상태를 현재 실행 결과에 잘못 적용하지 않는다. 기존 연구 결과·원자료·문서는 보존하며, 이 목표 파일의 사용자 요청 수정은 이전 버전을 보관한 뒤 반영한다.

연구 범위는 다음과 같이 고정한다.

1. 대상은 기존 cell의 연속적인 네트워크 트래픽량 예측이다. 신규 cell, 침입 탐지 분류, 도로 교통 예측으로 연구 문제를 바꾸지 않는다. 관련 분야는 방법론의 근거로 활용한다.
2. 최종 예측은 기존 RCTL이 담당한다. 핵심 TCN·LSTM·이중 잔차 구조와 실제 관측 자료를 이용한 학습을 유지한다. 원 논문과 다른 입력, target, 손실, 학습 단위가 필요하다면 변경 이유와 공정한 비교 방법을 명시한다.
3. clustering 단계에서 RCTL의 학습 결과·예측값·손실을 후보 선택, 병합 또는 임계값 조정에 사용하지 않는다. 소속과 설정을 고정한 뒤 RCTL로 가설을 확인하는 것은 허용한다.
4. 여기서 독립성은 RCTL을 호출하지 않고 clustering을 실행할 수 있다는 의미다. TabICLv2에 의존하는 판단을 모든 예측모델에 무관한 보장으로 확대하지 않는다.
5. TabICLv2는 연구의 실제 판단에 기여해야 한다. 모델을 제거해도 같은 정보와 비용으로 같은 판단을 할 수 있다면, 그 역할을 다시 설계한다. 다른 모델로도 구현 가능한 방법이라는 이유만으로 배제하지는 않는다.

## 2. 앞선 실패를 재발 방지 기준으로 정리한다

먼저 아래 항목을 ‘이전 주장 → 확인된 문제 → 이번 후보에 적용할 검사’로 정리하라. 반례가 적용되는 조건과 적용되지 않는 조건도 구분한다.

- 제안 내부의 고정 context 제약을 해결한 것을 원래 UPC·RCTL의 실제 문제를 해결한 것으로 설명하지 않는다.
- 공통으로 허용되는 예측값의 존재를 공동 학습이 그 값을 선택한다는 근거로 사용하지 않는다. 평균 오차 최소화, cell별 보호, 모델 수 감소의 목적을 구분한다.
- 분포 전체를 사용하는 규칙이 중앙값·변동 폭 또는 기존 손실 기준으로 환원되는지 먼저 확인한다.
- 유한한 공통 입력의 유사성을 전체 시간 구간의 유사성으로 확대하지 않는다. 관측 지원 부족, 희소 상태, 피크 누락을 함께 다룬다.
- 전체 calibration이나 많은 분위수 출력을 cell별·시간대별 추정 정확성의 증거로 사용하지 않는다.
- 병합 중 추가 추론이 없다는 사실만으로 전체 계산량이 작다고 주장하지 않는다. context 준비와 최초 추론 비용도 포함한다.
- 예측 관계 비교, 손실 기반 clustering, context 선택, cache, lag·달력·이웃 특징의 사용 자체를 신규성으로 내세우지 않는다.
- 작은 합성 예시가 통과했다는 사실을 실제 트래픽에서 유용하다는 근거로 바꾸지 않는다.

위 문제를 피했다는 것만으로 새 기여가 생기는 것은 아니다. 그다음에 해결할 독립적인 문제와 기존보다 나아질 이유가 있어야 한다. 반대로 완전한 이론 보장이 없다는 이유만으로 타당한 실증 연구까지 자동 기각하지 마라.

## 3. 최신 선행연구를 원리와 실행 과정까지 분석한다

실행일 기준으로 최신 원문, 수정 버전, 공식 코드, 공개 가중치와 후속 연구를 확인하라. 기존 목록은 검색의 출발점이며 종착점이 아니다. 검색 날짜, 검색어, 확인한 범위, 논문 버전, 코드 commit과 접근하지 못한 자료를 기록한다. 이미 확보한 원문은 재사용하고 변경된 부분을 중심으로 갱신한다.

초기 문헌 범위 점검에는 다음 축을 모두 포함한다. 이미 확보한 근거를 재사용하고, 이후 추가 조사는 제0.1절의 현재 문제와 미해결 질문에 맞춰 선택한다. 매 회차 모든 축에서 새 논문을 찾아야 한다는 뜻은 아니다.

| 조사 축 | 시작할 자료와 실제 확인할 내용 |
|---|---|
| 네트워크 트래픽 | UPC·RCTL, ISP traffic foundation models, MobiGPT, 모바일 트래픽 ICL. 측정 단위, 주기성, 피크, 희소성, 공간 관계, 실제 실패 조건을 확인한다. |
| 시계열과 표 모델 | TabPFN-ST-AR, TabPFN-TS, 다변량 PFN 예측, 공식 TabICL forecasting 기능과 최신 후속 연구. 시간 특징, 예측 horizon, 정규화, 외삽, 다변량 입력과 시계열 분할을 확인한다. |

가장 가까운 선행연구 3~5편은 반드시 본문·수식·알고리즘을 읽고, 핵심 주장에 코드 구현이 필요한 경우 공식 코드도 확인한다. 각 논문에 대해 아래를 작성하라.

1. 해결한 문제와 다루지 않은 문제.
2. 입력, 정답, 예측 대상, 묶는 단위와 사용할 수 있는 정보.
3. 실제 계산 순서와 계산 결과가 바꾸는 결정.
4. 최적화 목적과 이론적 결과에 필요한 가정.
5. 검증 데이터, 비교 방법, 통제 조건, 비용, 실패하거나 이득이 작았던 조건.
6. 현재 연구로 옮길 수 있는 부분과 옮길 수 없는 부분.
7. 원문의 어느 식·절·알고리즘·표·코드 위치가 위 해석을 뒷받침하는지.

초록이나 성능 순위만 요약하지 마라. ‘이 논문을 반영하여 입력 구성, 비교 규칙, 대상 문제 또는 비용 설계를 무엇에서 무엇으로 바꿨는가’를 기록한다. 채택하지 않는 연구도 그 이유를 설명한다.

각 조사에는 현재 문제 ID 또는 선정 중인 문제 후보와, 원인 가설·소속 규칙·구현/비용·최소 확인 중 무엇을 구체화했는지 연결한다. 새로운 정보가 없으면 같은 결론을 늘려 쓰지 않는다. 원문에 현재 traffic 문제의 직접 실험이 없다는 이유만으로 이식 가능한 원리를 기각하지 말고, 필요한 추가 가정과 이를 구분할 작은 확인을 판단한다.

이론의 독립 표본 가정을 시간 의존 자료에 그대로 적용하거나, 도로 속도·격자 활동량·기지국 부하·단말 처리량을 같은 문제로 취급하지 않는다. 공개 구현이나 데이터 접근이 확인되지 않은 자료를 실행 가능한 기준으로 표시하지 않는다. 관련 논문을 찾지 못한 사실만으로 최초성을 주장하지 않는다.

## 4. 알고리즘보다 먼저 해결할 문제를 고른다

먼저 기존 UPC·RCTL과 강한 단순 대안이 어떤 조건에서 잘 작동하고, 어떤 조건에서 중요한 손해를 남기는지 분석하라. UPC를 단순히 ‘전체적인 흐름만 보는 방법’이라고 축약하지 말고, 원문의 피크 시간·PCC 계산 대상과 실제 그룹 구성 과정을 확인한다.

후보 문제마다 아래 항목을 갖춘 문제 정의서를 만든다.

- 관측 가능한 상황: 어느 데이터 단위, 시간대, horizon, 관측량, 입력 조건에서 생기는가?
- 실제 손해: 평균 오차, 피크 오차, 모델 수, 학습·예측 비용 중 무엇이 얼마나 중요한가?
- 기존 방법의 한계: 어떤 계산 또는 가정 때문에 그 손해가 남는가?
- 존재 근거: 원문의 결과, 공개 자료에서 재현한 통계, 작은 확인 중 무엇이 있는가?
- 단순 해결책: 달력·일주기·주간 lag, 이웃 정보, 정규화, 계절 기준, local/global 모델만으로 없어지는 문제인가?
- TabICLv2가 제공할 정보: 앞선 방법에 없는 어떤 판단 정보를 얻을 수 있는가?
- 실패 조건: 어떤 관찰이 나오면 이 문제를 연구 주제로 삼을 이유가 없어지는가?

사용자가 우려한 ‘짧은 구간 모양만 맞추다가 하루·주간 흐름을 놓치는 문제’를 명시적으로 확인한다. 시간·요일·계절 이력·예측 horizon을 맞춘 뒤에도 문제가 남는지 살핀다. 이를 위한 특징 추가 자체는 기본 설계로 두고 신규성으로 세지 않는다.

원시 데이터가 있다면 모델 학습보다 먼저 문제의 발생 빈도, 영향 크기, 비교 가능한 입력 범위, 제외되는 cell·시간대의 비율을 확인한다. 없다면 접근 가능한 공개 데이터와 논문의 직접 증거를 확인한다. 데이터 부재를 문제의 존재나 부재로 해석하지 않는다.

주된 개선 목표는 하나로 정한다. 예를 들어 같은 실제 cluster 수에서 예측 오차를 줄이는 목표와 허용 오차 안에서 모델 수를 줄이는 목표는 다른 목표다. 나머지는 보조 지표와 비용 제약으로 둔다. 허용 오차나 최소 개선량을 결과를 본 뒤 유리하게 정하지 않는다. 업무상 기준이 없으면 임의의 합격 수치를 만들지 말고, 사전에 고정한 기준 성능의 변동과 비용·오차 관계를 통해 판단하는 방법을 제시한다.

### 먼저 구별할 두 오류와 원인 확인의 한계

`잘못 합친 손해`의 후보 징후는 같은 시간대·요일·최근 이력 등 최종 예측기에 제공한 조건에서 cell별 이후 관계가 반복적으로 다른 것이다. `불필요하게 나눈 손해`의 후보 징후는 파형·피크가 달라도 제공한 입력으로 구별 가능한 하나의 관계를 학습할 수 있는데, 분리로 자료가 줄면서 이후 오차가 커지는 것이다. 두 징후는 각각 공동 학습의 실패·자료 부족의 인과적 증명이 아니다.

관계 차이, 입력 겹침, 유한 자료량, 최적화 정책, 시간 변화와 평가 오차를 분리하여 기록한다. 동일 K·cell 수의 두 partition 비교와 K1 대 K4 비교는 서로 다른 질문이다. 저장된 train/validation/test 예측으로 구별할 수 없는 원인은 `식별 불가`로 표시하고, 이를 구별하는 최소 통제 비교를 먼저 설계한다. 원인을 구별하려는 확인과 최종 신규 알고리즘의 성능 확인을 혼동하지 않는다.

16개 cell·hourly·추가 시간 특징을 사용한 기존 pilot은 원 논문의 UPC 전체 재현이 아니다. 원 논문과 차이가 있다는 사실만으로 기존 후보의 실패를 무효화하거나 10분 해상도·대규모 자료에서 개선될 것이라고 주장하지 않는다. 전체 자료를 다시 읽거나 대규모 학습하기 전에, 다음 판단에 필요한 차이 하나만 특정한다.

## 5. TabICLv2를 써야 하는 이유를 결정 과정과 연결한다

모델의 사전학습 목적과 데이터 가정, 열·행·context 처리, target 정보의 사용, 회귀 출력, 전처리와 cache를 공식 원문·코드에서 확인하라. 각 특성이 선택한 문제의 어떤 계산에 도움이 되는지 설명한다. 최신 API와 checkpoint에서 실제로 사용할 수 있는지도 확인한다.

최소한 다음을 구분한다.

- 고정된 신경망 파라미터와 context에 따라 달라지는 전처리·내부 표현·attention·예측값.
- 가중치를 다시 학습하지 않는 것과 새 context의 추론 준비 비용이 없는 것.
- 내부 분위수 출력, API 반환 분위수, mean·median의 선택과 평가 손실.
- 동일 context의 cache 재사용과 서로 다른 context의 계산을 섞는 행위.
- 표현을 추출할 수 있다는 사실과 서로 다른 context·cell의 표현 거리를 비교해도 된다는 근거.
- attention이 큰 sample과 그 sample이 예측이나 공동 학습에 실제로 기여한다는 주장.

회귀용 TabPFN, 단순 회귀·분위수 추정, kernel 또는 최근접 sample 기준으로 같은 역할을 구현했을 때와 비교하라. TabICLv2만 가능한 방법일 필요는 없다. 그러나 선택 이유는 반복 학습 비용, 작은 자료에서 얻는 정보, 입력 간 비선형 관계 등 실제 설계에 연결되어야 하며, 우월성을 아직 관찰하지 않았다면 가설로 표시한다.

각 후보에서 ‘TabICLv2가 계산한 무엇이 달라져서 어떤 clustering 결정이 바뀌는가’를 한 문장과 작은 예시로 제시한다. 이 질문에 답하지 못하면 이름만 붙인 적용으로 보고 재설계한다.

## 6. 후보를 비교하고 실패 원리에 따라 계속 재설계한다

한 차례에 최대 세 개의 후보를 구체적으로 비교한다. 이는 탐색을 끝낼 후보 수의 상한이 아니라 한 번에 검토할 작업량의 상한이다. 후보들이 같은 규칙에 이름이나 보정항만 바꾼 형태가 되지 않도록 한다.

여러 제목을 늘어놓기보다 먼저 근거가 가장 강한 오류 하나의 후보 명세를 완성한다. 기존 후보 인덱스에 기록된 원리는 이전의 실패 원인 또는 미확인 연결을 실제로 바꾸는 차이가 있을 때만 재검토한다. `문헌상 중복`, `논리 반례`, `실제 실행 실패`, `미확인`을 별도 상태로 두며, 미실행을 실패로 또는 미확인을 유망함으로 바꾸지 않는다.

후보 명세에는 적어도 입력·target·horizon, context/query 생성과 시간 경계, TabICLv2의 출력과 호출 위치, 후보 검색·배정·갱신·종료를 포함한 소속 결정식 또는 의사코드, RCTL에 넘길 실제 자료, 단순 대체안, 최대 호출·예측 행·학습 횟수, 기각 조건을 채운다. 같은 입력·정답·후보 목록을 사용하는 단순 추정기 치환을 비교할 수 있도록 한다. 이미 좋은 것으로 알려진 교환 하나의 점수 개선은 후보 검색·선택 알고리즘의 검증을 대신하지 않는다. 같은 결정의 계산·추정 효율 개선도 가능하지만, 출발하는 결정이 유용하다는 근거가 있어야 한다.

각 후보를 아래 연결로 설명하라.

**실제로 남는 문제 → 기존 방법이 놓치는 이유 → 새로 추정할 정보 → TabICLv2의 역할 → 바뀌는 결정 → 최종 예측 또는 비용이 개선될 원리 → 추가 비용 → 실패 조건**

다음 다섯 검사를 통과하지 못한 후보는 추천하지 않는다.

이는 최종 추천의 기준이다. 알려진 구성 요소를 사용하거나 아직 실증 결과가 없다는 이유만으로 제0.1절의 작은 검증 진입을 막지 않는다. 단순 적용의 실용적 효용과 논문 기여의 차별성은 별도로 판단한다.

1. **필요성:** TabICL을 도입하기 전에도 존재하는 문제이며, 단순한 입력 보강으로 해결되지 않는가?
2. **차별성:** 가장 가까운 기존 방법과 입력·정보·목표·결정 규칙을 나란히 비교했을 때 실제 차이가 있는가?
3. **동등성:** 표기, 좌표, 정규화, 단조 변환을 정리하면 기존 거리·손실·중앙값 기준과 같은 결정이 되는가? 같다면 계산 또는 통계 효율에서 별도의 실질적 이득이 있는가?
4. **연결성:** 새 점수가 좋은 이유가 최종 연구 목표와 연결되는가? 다른 모델의 성능을 대변한다는 미확인 가정 하나에 전부 의존하지 않는가?
5. **현실성:** 필요한 데이터·모델 기능을 실제로 쓸 수 있고, 전체 비용이 강한 단순 대안과 비교하여 감당 가능한가?

차별성을 ‘기존 논문이 제안 방법을 사용하지 않았다’로 설명하지 마라. 기존 방법이 놓치는 상황과 제안이 다른 결정을 내리는 이유를 설명해야 한다. 서로 다른 결정을 내린다는 사실과 그 결정이 더 낫다는 근거도 구분한다.

탈락 원인에 따라 다음 행동을 정한다.

- 실제 문제가 약하면 알고리즘을 더 만들지 말고 다른 문제를 찾는다.
- 기존 방법과 동등하면 불필요한 부분을 제거하고, 남은 비용·추정 이득이 연구가 되는지 다시 본다.
- TabICLv2 정보가 불안정하면 그 정보가 덜 필요한 다른 판단 규칙을 검토한다.
- 최종 학습과 연결되지 않으면 모델 수·손실·자료량·모델 용량의 관계부터 다시 정리한다.
- 계산량이 크면 전체 쌍 비교와 반복 추론을 줄이는 구조를 먼저 검토한다. 후보 수 제한으로 놓치는 유용한 조합도 보고한다.

탈락 이력에 ‘무엇이 반박되었는가, 어느 가정이 원인인가, 다음 후보가 그 원인을 어떻게 바꾸는가’를 기록한다. 동일한 반례를 설명 문장만 바꾸어 반복 제출하지 않는다. 모든 후보가 탈락해도 이를 목표 완료로 표시하지 말고 다음 문제·원리의 후보를 탐색한다.

## 7. 최종 학습과의 연결을 현실적인 수준에서 확인한다

RCTL을 clustering 내부에 넣지 않으면서도 제안한 규칙이 왜 유용할 수 있는지 다음을 분리하여 설명하라.

1. 참 예측 관계를 안다고 가정할 때의 충돌과 공유 가능성.
2. 유한한 자료를 함께 사용하여 추정 오차가 줄어드는 이득.
3. 시간·이력·이웃 입력으로 다른 cell을 구별할 수 있는 정도.
4. RCTL의 입력 길이, 모델 용량, 실제 학습 목적과의 관계.
5. TabICLv2의 추정 오차와 미래 분포 변화가 판단에 미치는 영향.

참 관계가 다르다는 이유만으로 공동 학습이 나쁘다고 판단하지 마라. 참 관계가 같다는 이유만으로 충분한 자료가 이미 있는 cell에 공유 이득이 크다고 판단하지도 마라. 이 둘을 구별하는 것이 제안의 개선 원리에서 필요한지 확인한다.

가능하면 단순화한 조건에서 필요한 성질·충분조건·실패 반례를 확인한다. 알 수 없는 상수를 작다고 가정하여 보장을 만들지 않는다. 정리가 어렵다면 직접 관찰 가능한 중간 현상과 최소 확인으로 연결한다. ‘보장이 없으니 탈락’과 ‘실험하면 알 테니 채택’ 사이에서 증거의 강도에 맞춰 판단하라.

RCTL의 사후 확인 결과를 반복해서 보면서 규칙·임계값을 조정하면 모델에 대한 의존성이 생긴다. 이를 숨기지 않는다. 후보 확인용 구간과 최종 평가 구간을 분리하고, 수정에 사용한 구간을 독립 검증이라고 다시 부르지 않는다.

## 8. 선택 가능한 후보는 구현 수준까지 구체화한다

추천 후보에는 다음 항목을 빠짐없이 정한다. 빈칸이나 ‘적절히 선택한다’는 문장으로 핵심 결정을 넘기지 않는다.

- 데이터셋과 관측 단위, 적격 cell 선정, sample의 입력 열·입력 길이·target·horizon.
- 주기·시간대·요일·공간 정보와 실제로 사용할 수 없는 정보.
- 결측, 정규화, 단위 복원, cell·시간대별 손실 비중.
- sample을 생성하는 시점, context와 query의 역할, 사용 가능한 정답의 시간 경계. 무조건 하루를 비우는 방식 대신 누출 방지와 별도 의존성 확인 목적에 맞춰 간격을 정한다.
- context 선택·크기·갱신, query 선정·고정·변경 조건. input을 고르는 데 미래 target을 사용하지 않는다.
- 후보 검색 방법, cell당 후보 수와 전체 후보 수, 대칭화·중복 제거, 임계값 결정 근거.
- TabICLv2의 실제 호출 위치·입출력·회귀 출력 선택·cache·반복 횟수.
- clustering 점수, 병합·배정·거절·보류, 갱신 범위, 종료 조건, 목표 cluster 수와 실제 cluster 수의 차이 처리.
- 최종 소속을 고정한 뒤 전체 실제 자료를 RCTL로 넘기는 과정. TabICLv2 예측을 RCTL의 정답으로 바꾸지 않는다.
- 의사코드, 작은 수치 예시, 각 단계의 입력·처리·출력 표.

구체적인 기본값은 데이터, 공식 모델 제한, 비용 또는 선행연구를 근거로 정한다. 설계상의 초기값과 검증된 최적값을 구분한다. 불필요한 하이퍼파라미터를 추가하지 않는다.

전체 비용은 전처리, 후보 검색, context 준비, 추론, query 수, 상태별 반복, 병합 후 갱신, 저장 공간, RCTL 학습까지 합산한다. cell 수 N, context 수 M, query 수 Q, cell당 후보 수 k, 반복 수 R을 명시하여 계산식을 제시한다. 128·1,024·10,000개 cell 규모에서 작업량을 산출하되 실제 측정 시간과 산술 추정을 구분한다.

전체 쌍 계산을 먼저 한 뒤 상위 후보만 남기면서 처음부터 계산량을 줄였다고 주장하지 않는다. cluster 수 감소가 전체 학습 자료량이나 총 optimizer step 감소와 같은 의미인지도 확인한다. UPC 및 동일 정보를 cache한 단순 대안과 공정하게 비교한다.

## 9. 큰 실험 전 최소 확인을 실제로 수행한다

검토 순서는 원문·코드·논리 확인 → 학습 없는 데이터 진단 → 필요한 경우 작은 TabICLv2 추론 → 규칙과 소속을 고정한 작은 RCTL 확인이다. 한 후보가 앞 단계에서 실패하면 그 후보의 비싼 실행을 멈추고 다른 후보의 설계로 돌아간다. 연구 방향 탐색 자체를 종료하지 않는다.

각 확인을 시작하기 전에 다음을 파일에 고정한다.

- 확인할 핵심 주장 하나, 가능한 결과와 결과별 수정·기각·진행 행동.
- 비교할 가장 강한 단순 대안과 가장 가까운 선행 방법.
- 같은 정보량, 같은 실제 cluster 수 또는 같은 총예산 중 어떤 비교인지.
- 데이터와 시간 분할, seed, sample·context·query 수, 추론 준비 횟수, 예측 행 수, 학습 횟수.
- 필요한 최소 개선량 또는 동등성 범위의 근거, 변동 확인 방식, 판단 불가 조건.
- 이번 goal의 누적 사용량, 이번 실험의 비용 상한과 필요한 제9.1절의 증액. 후보를 바꿔도 이미 사용한 비용을 초기화하지 않는다.

먼저 참 관계를 아는 예에서 규칙 자체를 확인하고, 제안이 필요 없는 조건과 오히려 실패하는 조건도 포함한다. 합성 확인은 논리 오류와 동등성을 찾는 용도이며 실제 문제의 중요성을 대신하지 않는다.

실제 자료를 확보할 수 있다면 발생 빈도와 효과 크기의 작은 진단을 수행한다. 모델 실행이 필요하면 장비와 데이터 조건을 확인한 뒤 4개 cell의 동작·비용 확인부터 시작하고, 필요할 때 16개, 최대 32개까지 확대한다. 이는 사전 검토의 비용 범위이며 통계적 충분성을 보장하는 숫자가 아니다. 필요한 독립 시간 블록이 확보되지 않으면 cell 수만으로 성공을 선언하지 않는다.

최초 모델 동작 확인은 최대 4개 cell, cell당 context 256개·query 64개, context 준비 1회·예측 호출 1회로 제한한다. 총 query 상한은 256행이다. 이는 API 동작과 비용을 확인하기 위한 상한이며 연구 알고리즘의 최적 설정이 아니다. 장비가 부족하면 줄이고, 실제 ensemble 수와 내부 추론 작업도 따로 기록한다. 이후 확대 여부와 누적 상한은 이 비용 측정과 확인할 주장에 필요한 작업량에서 정한다.

이번 범위에서 대규모 RCTL 학습, 광범위한 튜닝, 유료 연산을 시작하지 않는다. 숫자로 된 누적 호출·행·학습 상한은 실제 장비와 첫 비용 확인에서 정하고, 성능 결과를 보기 전에 고정한다. 큰 원시 자료·checkpoint를 받기 전에 필요한 크기와 최소 대안을 확인한다.

작은 RCTL 확인은 단순 모델의 결과로 대체하여 통과 처리하지 않는다. 같은 입력·실제 cluster 수·학습 조건을 사용하고, 수렴 실패와 연구 아이디어의 실패를 구분한다. 이전의 부정적 결과를 피하려고 어려운 cell이나 시간대를 제외하지 않는다.

비교 설계에는 원래 UPC+RCTL, 제안과 같은 시간·공간 입력을 준 UPC+RCTL, 단일 global RCTL, 적절한 단순 clustering+동일 RCTL을 포함할 필요가 있는지 검토하라. TabICLv2의 기여는 같은 알고리즘에서 단순 추정기 또는 회귀용 TabPFN으로 대체하는 비교로 분리한다. 이 비교들을 모두 사전 검토에서 실행할 필요는 없다. 핵심 가정에 가장 결정적인 비교부터 실행하고 나머지는 본 실험 계획으로 구분한다. 실제 cluster 수를 맞출 수 없으면 공통으로 비교 가능한 오차·모델 수 범위를 제시한다.

실행할 수 없는 항목은 미실행으로 기록한다. 무엇이 부족한지, 결정을 바꾸는 최소 관찰은 무엇인지, 그때까지 어떤 주장을 할 수 없는지 적는다. 상한에 도달하면 새 대규모 실행을 시작하지 말고 기존 증거로 판단 가능한 후보를 계속 분석한다.

### 9.1 실험 계획에 근거한 자율 예산 편성

2026년 9월 28일 사용자는 매번 승인을 기다리지 않고 연구에 필요한 상한을 늘리는 방향을 요청했다. **기존 소규모 로컬 연구 범위에서, 구체적인 실험 계획과 비용 근거를 먼저 기록하면 추가 사용자 승인 없이 필요한 누적 상한을 최소한으로 증액할 수 있다.** 이 규칙은 이전의 ‘새로운 사용자 승인 없이 상한을 바꾸지 않는다’는 규정을 대체한다. 자동 재개 자체는 증액 사유가 아니며 이미 사용한 비용은 계속 누적한다.

실제 사용량·현재 상한·진행 중 예약·증액 이력은 `tmp/redesign_20260925/cumulative_execution_budget.json`을 기준으로 확인한다. 다음은 이 정책 변경 직전의 누적 편성값이다. 영구 고정 상한이 아니며, 이후 실제 편성과 잔여량은 최신 원장이 우선한다. 이번 운영 정책 수정만으로 실행 횟수를 미리 늘리거나 모델을 실행하지는 않았다.

| 누적 항목 | 정책 변경 직전 편성값 |
|---|---:|
| TabICLv2 context 준비 | 110회 |
| TabICLv2 query 예측 행 | 71,872행 |
| TabICLv2 fit·predict 계산 | 989.0795223000118초 |
| RCTL optimizer 학습과 통계 적응을 합한 실행 | 62회 |
| RCTL 누적 epoch | 3,254 |
| RCTL 계산 시간 | 3,458.1391634초 |
| 단순 모델·수치 계산 | 600초 |
| 전체 로컬 모델링 계산 | 6,000초 |

초기29회 이후의 추가18회 편성 및 단계160의 일회성 범위 조정은 이미 집행된 이력으로 보존한다. 이번 확인 시 RCTL은 optimizer53회와 통계 적응9회를 합한62회를 사용해 현재 편성 잔여량이0회다. TabICLv2는105context·68,440행을 사용해5context·3,432행이 남아 있다. **잔여0회는 현재 편성분 소진을 뜻하며 연구 중단이나 추가 승인 대기를 뜻하지 않는다.** 필요한 확인이 있으면 아래 절차로 상한을 편성한 뒤 실행한다. 이 수치는 정책 변경 시점의 기록이며 다음 실행 전에 최신 원장을 다시 읽는다.

1. **판단을 바꿀 최소 실험을 정한다.** 실제 문제와 후보 명세, 반박 가능한 주장, 가장 중요한 비교군, 데이터·소속·seed·평가 조건, 결과별 진행·기각·수정 결정을 파일에 고정한다. `candidate_decision_index.md`와 기존 산출물을 대조해 재사용할 부분을 뺀다. 후보의 성공을 미리 입증할 필요는 없다. 실행 결과가 어떤 판단도 바꾸지 못하는 반복 진단에는 증액하지 않는다.
2. **필요량을 산정한다.** 하나의 고정된 실험과 필수 비교에 필요한 추가 context·query·optimizer 학습·통계 적응·epoch·계산 시간·메모리 및 실행 중단 기준을 적는다. 기존 측정값을 우선 사용하고 추정치와 여유분의 근거를 구분한다. 기존 cell 최대32개, CPU4thread 이내, 추가 optimizer 학습의 fit당80epoch 이하 조건을 유지한다. 대규모 실험·광범위한 튜닝·유료 연산은 이 자율 편성 범위에 포함하지 않는다.
3. **부족한 항목만 증액하고 예약한다.** 사용량과 미정산 예약을 포함해 필요한 추가량을 구한다. 각 항목의 새 상한은 기존 상한과 ‘누적 사용량 + 미정산 예약 + 이번 실험에 필요한 예약량’ 중 큰 값으로 정한다. `autonomous_cap_adjustments`에 고유 ID, 일시, 계획 파일, 판단 목적, 변경 전·후 상한과 차이, 사용량·예약, 비용 근거와 중단 기준을 남긴다. 이에 맞춰 원장의 `caps`, 현재 잔여량, 새 실행 허용 여부 및 해당 회차의 예약을 함께 갱신한 뒤 실행한다. 과거 회차의 한도·사용량을 덮어써 새 여유가 생긴 것처럼 만들지 않는다. 다른 실행이 예약을 변경했다면 최신 원장을 다시 읽어 중복 배정하지 않는다.
4. **계획대로 실행하고 정산한다.** 정한 조건과 실험별 상한을 넘기지 않는다. 실패·중단 비용도 기록하고 사용하지 않은 예약만 해제한다. 모델 실행 뒤 결과에 맞춰 상한을 소급 확대하지 않는다. 완료된 실험은 반복하지 않으며, 실패한 실행도 원인과 재실행의 필요성이 달라진 별도 계획 없이 반복하지 않는다. 다음 증액은 앞 실험의 정산과 결과별 판단을 반영해 편성한다. 같은 원리의 이름 변경이나 단순한 시간 경과는 증액 근거가 아니다.
5. **연구 기준을 유지한다.** RCTL 확인은 clustering 규칙과 소속을 먼저 고정한 뒤 수행하고, RCTL 결과를 소속 선택이나 반복 튜닝에 되먹이지 않는다. 개발 자료의 결과를 독립 검증으로 표시하지 않는다. 직접 실행하지 않은 RCTL 개선은 미검증으로 남긴다. 예산 운영 변경 자체도 연구 성과로 세지 않는다.

RCTL 실행 수는 optimizer 학습과 통계 적응의 합으로 계산한다. `used.RCTL_fits`는 optimizer 학습만 뜻하므로 `caps.RCTL_fits`에서 이 값만 빼지 않는다. 호환용 `caps.RCTL_fits`와 `caps.RCTL_fit_or_adaptation_runs`는 같은 합산 상한을 유지하고, epoch·RCTL 시간·전체 로컬 모델링 시간도 함께 확인한다. TabICLv2와 단순 수치 계산의 누적 상한에도 같은 편성 절차를 적용한다.

과거 원장의 `automatic_recharge: false`, 개별 계획의 `budget_recharge: false`는 무근거 자동 충전 금지를 뜻한다. `new_RCTL_fits_permitted_under_current_cap: false`와 잔여0은 아직 증액·예약하지 않은 현재 편성 상태다. 이 값이나 과거 기록의 승인 필수 문구를 이번 사용자 요청에 따른 자율 편성 권한의 금지로 해석하지 않는다. 새 실행 코드의 허용 여부는 최신 상한과 해당 계획의 예약에서 계산한다.

상한 변경은 근거와 실제 비용을 연구 기록에 남기고 의미 있는 결과와 함께 알린다. 같은 승인 질문이나 예산 부족 보고를 반복하지 않는다. 기존 범위를 벗어나는 자원이 필요하면 그 필요성과 가능한 대안을 구체화해 사용자에게 알린다. 이 정책은 연구 파일의 실행 예산에 관한 것이며 앱 사용량 제한, native goal의 토큰·시간 제한이나 사용자의 중단 요청을 변경하거나 우회하지 않는다.

### 9.2. 고정 소속의 작은 RCTL 연결 확인

실행 가능한 후보 또는 관측 문제의 유용성 판단을 바꿀 고정 소속이 있으면, 모든 Tab–RCTL 불일치 원인이나 최종 신규성의 완전한 해명 없이 작은 RCTL 확인으로 들어갈 수 있다. 후보 규칙·검색 절차·최종 소속은 RCTL 실행 전에 고정한다. 기존 고정 소속의 연결 진단은 새 Tab 알고리즘의 검증과 별도로 표시한다.

현재 고정 3217↔3302 교환의 같은 조건 RCTL 효용이 미검증이면, 완료된 한정 비교를 재사용한 뒤 이 연결 확인을 우선 계획한다. 출발 소속은 UPC 자체가 아니라 profile D32다. 소규모 UPC U32, 단순 profile D32, D32의 고정 교환 소속을 구별하고, 동일한 32cell·실제 K4에서 필요한 비교를 설계한다. 세 소속의 비교는 UPC 대비 효용, 단순 군집 대비 효용, 관측한 자료 공유 이득의 연결을 분리한다. 더 최근에 같은 조건의 RCTL 결과가 완료됐으면 그것을 재사용하며 이 고정 교환을 다시 실행하지 않는다.

| 실행 전 고정할 항목 | 적용 기준 |
|---|---|
| 확인할 주장과 비교군 | UPC·강한 단순 군집·고정 교환의 같은 K 효용을 구분한다. HGB와 Tab이 같은 소속을 선택했으면 동일 RCTL을 두 번 학습하지 않는다. Global K1은 필요할 때 별도의 분할 필요성 비교로 해석한다. |
| 입력·자료·모델·학습 | 같은 cell cohort·실제 K·RCTL 구조·입력·척도·학습/validation/평가 구간·seed·optimizer·종료 조건을 고정한다. cluster별 전체 실제 sample·정답을 사용하며 Tab context·예측으로 대체하지 않는다. |
| 정보 조건의 차이 | Tab의80열과 기존 RCTL8×9 등의 차이는 필요한 연결 가정으로 기록한다. 입력을 바꾸려면 문제·사용 조건의 근거를 먼저 적고 같은 입력을 준 UPC·단순 군집 RCTL을 비교한다. 서로 다른 입력·16/32cell·기간의 결과를 같은 조건으로 합치지 않는다. |
| 재사용과 학습 수 | 같은 자료·입력·구성·학습 조건의 완료 모델과 변하지 않은 cluster만 재사용한다. 세 소속을 모두 새로 학습하면 한 seed 기준 최대12개 cluster 모델이며, 이는 자동 학습 예약이 아니다. 실제 추가 fit·통계 적응·epoch·시간·메모리를 계산한 뒤 제9.1절로 부족분만 증액·예약한다. |
| 효과와 불확실성 | 주지표·최소 개선량 또는 판단 불가 범위의 근거, 전체/사전 시간 블록/cell별 손익, 구현·학습 실패 기준을 정한다. 수치 부호용−1e−10을 실질적 개선이나 통계적 확신의 기준으로 쓰지 않는다. 변동 근거가 부족하면 작은 개발 확인의 증거 수준으로 해석하며 이를 실행 금지 이유로 만들지 않는다. |
| 시간 사용 이력 | 이미 조사·후보 선택·수정에 사용한 구간은 개발 자료다. 독립 평가용 미사용 구간은 사용 이력부터 확인한다. 없으면 미확인으로 남기며 cell 수만으로 독립 검증을 주장하지 않는다. |
| 추가 확인 | 필요한 seed 또는 시간 블록 확인을 주장과 변동 근거에 맞춰 사전 계획한다. 유리한 seed·기간을 찾을 때까지 검색하지 않는다. 다른 조건으로 바꿨다면 별도의 새 비교로 표시한다. |

결과가 UPC·D32 대비 유리하면 현재 조건의 자료 공유 이득을 지지하는 근거로 보존하고, 후보 검색·선택 규칙과 같은 정보 단순 추정기 비교로 Tab의 추가 기여를 확인한다. 단순 대안과 동일하면 실용적 효용과 Tab의 기여를 분리한다. Tab 점수는 개선했지만 RCTL이 악화하면 이 고정 규칙의 연결 가설을 닫으며, 어떤 규칙을 실제로 바꿀 새 근거가 있는 경우에만 제한된 후속 분석을 한다. 혼재·작은 효과는 사전 계획한 불확실성 확인 또는 판단 유보로 처리하고, 학습 실패는 성능 기각과 구분한다.

어느 결과에서도 같은 RCTL 확인을 보며 소속·임계값·cell·K를 반복 조정하지 않는다. 결과로 이 후보의 효용을 사후 판단하는 것과 RCTL을 clustering의 내부 점수로 사용하는 것을 구분한다. 단순 대안 이후 중요한 잔여 문제나 구별 가능한 후보가 없으면 제0.2절에 따라 문제를 전환한다. 고정 교환의 긍정 결과만으로 신규성·Tab 고유 효용·최종 goal 완료를 선언하지 않는다.

## 10. 신규성과 개선 근거를 별도로 판정한다

최종 후보에 대해 다음 세 표를 작성한다.

**첫째, 가장 가까운 연구와의 비교표.** 대상 문제, 사용 정보, 결정 규칙, 학습·추론 비용, 보장 또는 실증 범위, 남은 한계를 같은 열로 비교한다. 기존 방법에 없는 요소뿐 아니라 기존 방법보다 유리해지는 조건을 보여라.

**둘째, 주장과 증거의 대응표.** 주장마다 원문·공식 코드·수학적 확인·실제 관찰·남은 가정 중 무엇인지 표시한다. 실행일의 검색 범위 안에서 확인한 신규성과 전 세계 최초라는 단정을 구분한다.

**셋째, 가장 강한 반론과 답변표.** 최소한 다음을 다룬다.

- 단순한 계절·시간 특징 보강 또는 기존 clustering으로 충분하지 않은가?
- 최신 TabPFN이나 단순 회귀로도 같은 결과를 낼 수 있지 않은가?
- 기존 예측 기반 clustering에 모델 이름만 바꾼 것 아닌가?
- TabICLv2에서 유용한 기준이 RCTL에도 유용하다는 연결은 무엇인가?
- 추가 정보, 더 많은 sample, 다른 cluster 수 또는 더 큰 계산 예산 때문에 좋아지는 것 아닌가?
- context 선택과 반복 검증에 과적합한 것 아닌가?
- 이득이 없을 때 모듈 추가 없이 무엇을 단순화할 수 있는가?

기여는 한 문장으로 작성한다. 그 문장 안에 실제 문제, 바꾼 원리, 기존보다 개선되는 판단 또는 비용이 들어가야 한다. ‘TabICLv2를 최초 적용했다’, ‘더 정교한 관계를 반영한다’, ‘여러 장점을 결합했다’만으로 쓰지 않는다.

## 11. 산출물과 완료 조건

별도 파일로 다음을 제공하라.

1. **한국어 연구 방향 재설계 보고서:** 첫 부분에 추천 방향 하나, 해결할 문제, 선행연구 대비 차이, 개선 원리, 지금 확인한 근거, 남은 불확실성을 제시한다. 뒤에 원문 분석, 후보 탈락 이력, 알고리즘, 비용, 최소 확인 결과를 둔다.
2. **교수님께 드릴 Word 문서:** 문제와 연구 흐름을 직관적으로 설명하되, 알고리즘은 구현 가능한 수준으로 적는다. 복잡한 수식과 어려운 이름으로 빈 논리를 가리지 않는다. sample, cell, context, query, clustering을 사용하고 ‘사례’는 사용하지 않는다. 모든 페이지를 렌더링하여 검수한다.
3. **근거 자료:** 출처·버전 기록, 핵심 비교표, 실제 실행 코드·설정·결과, 미실행 목록, 누적 비용 기록. 수행하지 않은 검증을 결과처럼 제시하지 않는다.

결과 파일은 `output/research/`와 `output/docx/`에 기존 문서와 구분되는 이름으로 저장한다.

제0.2절의 문제별 판단 완료, 부정적 결과로 개별 방법을 닫는 것, 고정 소속의 RCTL 연결 확인은 중간 판단이다. 운영 수정이나 비교 완료만으로 연구 성과·Tab의 신규성·전체 goal 완료를 선언하지 않는다. 최종 후보의 소속 선택 알고리즘, Tab의 추가 기여, clustering→RCTL 연결에 대한 직접 근거는 별도로 확인한다.

목표 완료는 다음 조건을 모두 충족할 때만 선언한다.

- 연구할 문제의 실재성과 중요성에 직접 근거가 있다.
- 가장 가까운 선행연구와의 차이를 원리와 결정 수준에서 설명했다.
- TabICLv2의 역할과 더 단순한 대안을 쓰지 않는 이유를 설명했다.
- 같은 정보·비용 조건에서 개선될 원리에 근거가 있고, 핵심을 무너뜨리는 알려진 반례를 처리했다.
- clustering → RCTL 연결에 필요한 가정을 구체적으로 좁혔으며, 핵심을 모두 본 실험으로 넘기지 않았다.
- 구현 세부와 누적 비용, 최소 확인 결과가 있어 착수 여부를 판단할 수 있다.
- 적어도 하나의 추천 방향을 선택했고, 남은 본 실험의 질문과 실패 시 행동을 정했다.

한 후보의 기각, 참고문헌 목록, 추상적인 아이디어, 검증 계획만으로는 완료하지 않는다. 부족한 근거가 무엇인지에 따라 문제 선정·문헌 분석·알고리즘 설계·작은 확인 중 필요한 단계로 돌아가라. 기존 실패와 같은 상태를 더 긴 문서로 반복하지 않는다.

실제 외부 제약 때문에 어떤 후보도 더 판단할 수 없는 경우에는 근거를 꾸며 완료하지 마라. 완료하지 못했다는 사실, 독립적으로 진행한 대체 탐색, 부족한 자료 또는 자원, 가장 작은 해소 조건을 명시하고 재개할 수 있게 남긴다. 단순히 어렵거나 불확실하다는 이유로 이 예외를 사용하지 않는다.

## 12. goal 자동 재개의 연구 진행 규칙

자동 재개의 목적은 미완료 연구 작업의 실행이다. 이미 답변한 사용자의 연구 방향 질문에 다시 답하거나, 사용자 의견에 동의하는 문장으로 회차를 채우지 않는다. 다음 순서로 진행한다.

**프롬프트 출력 관문:** goal 프롬프트 본문·복사용 코드블록은 현재 들어온 실제 사용자 요청이 그것을 새로 요구할 때만 출력한다. 자동 재개 본문, 압축된 대화 요약, resolved_requests 또는 과거 일반 질문에 같은 문장이 남아 있는 것은 새 요청의 증거가 아니다. '프롬프트 반복을 해결하고 목표를 진행하라'는 요청은 운영 수정 후 연구 실행을 요구하므로 프롬프트를 제공하지 않는다. 응답 직전에 현재 호출의 종류와 산출물이 일치하는지 확인한다. 이 관문을 수정했다는 보고도 자동 재개마다 반복하지 않는다.

1. **이번 실제 입력으로 호출을 구분한다.** 새 사용자 요청이면 직접 처리한다. `<codex_internal_context source="goal">`로 전달된 회차는 goal 연구 재개이므로 `research_state.json`의 `next_action`부터 이어간다. 압축 요약·과거 대화·파일에 인용된 태그와 저장된 `current_request_kind`는 이번 호출의 증거가 아니다. 대화 이력의 마지막 일반 질문을 다시 답하지 않으며 `resolved_requests`는 새 요청이나 판단을 바꾸는 근거가 있을 때만 연다.
2. **현재 상태만 복원한다.** `AGENTS.md`, 이 목표의 변경된 부분, `research_state.json`, `research_focus.md`, `progress.md`의 최신 연구 항목, 해당 상세 기록, 후보 인덱스와 누적 원장을 확인한다. 제0.1절의 초기 통합 검토는 완료 범위부터 이어가고 완료 후에는 변경분만 반영한다. 전체 과거 기록이나 출발 문헌을 매번 다시 읽지 않는다. 실제 결과·실행 표시·정산 기록과 상태 파일이 어긋나면 실제 기록으로 먼저 고친다. 과거 계획의 ‘다음 행동’을 최신 작업으로 잘못 실행하지 않는다.
3. **미완료 행동 하나를 실제로 수행한다.** 현재 집중 문제 또는 선정 중인 문제, 확인할 주장, 사용할 자료·비교, 결과별 결정을 먼저 적는다. 새 지침과 기존 다음 행동의 연결을 검토해 유지·보완·전환을 기록하되 진행 중 결과를 버리지 않는다. 이미 끝난 작업은 재실행하지 않는다. 현재 후보가 기각되면 실패 원인이 현재 문제에 대해 무엇을 바꾸는지 판단하고 다음 행동을 정한다. ‘계속 검토하겠다’는 문장이나 파일 번호 증가를 연구 진전으로 세지 않는다.
4. **결과와 다음 행동을 인계한다.** `progress.md`에는 해결한 질문·근거·달라진 판단·비용·다음 행동을 기록한다. `research_focus.md`의 미해결 질문과 판단을 갱신하고, `research_state.json`에는 집중 문제의 참조와 최신 완료 연구, 진행 중 실행 여부, 다음 행동의 입력·작업·결과별 결정과 필요한 예산을 갱신한다. 사용자 요청에 따른 목표·지침 수정은 운영 작업으로 분류하고 최신 연구 단계를 대신하지 않게 한다. 원장과 후보 인덱스는 변경이 있을 때 함께 갱신한다.
5. **실제 수행 내용과 일치하는 새 결과를 알린다.** 응답 직전에 이번 실제 입력, 실행 기록, 산출물과 정산을 대조한다. 연구를 수행했다면 그 결과·한계·다음 행동을 보고하며 ‘이번에는 연구를 실행하지 않았다’고 결론내리지 않는다. goal이 active인 것은 goal 자신의 실행을 건너뛸 이유가 아니다. 의미 있는 새 결과·완료·실행 실패·필요한 사용자 조치만 알리고 같은 결론·예산 부족·goal 입력 안내·운영 수정을 반복 보고하지 않는다.

한 후보의 부정적 결과를 TabICLv2 또는 독립적 clustering 전체의 기각으로 확대하지 않는다. 반대로 성공한 수치 하나를 신규성·RCTL 개선의 증거로 확대하지 않는다. 다음 단계가 준비되고 허용 범위에 있으면 재입력을 기다리지 않고 이어간다. 가능하지만 어렵다는 이유로 분석을 멈추지 않으며, 새 근거 없이 같은 실패 원리로 되돌아가지 않는다.

앱 goal의 상태와 파일의 연구 진행 상태는 별개다. `106_continuation_state.json` 등 과거 설정으로 현재 앱 상태를 추정하지 않고 실제 조회 결과만 사용한다. 파일 수정으로 native goal이 재개·완료되었다고 주장하지 않는다. 사용자의 pause·중단 및 앱 사용량·예산 제한을 존중하며 goal 상태 변경은 해당 도구의 상위 지침을 따른다.

삭제된 예약 작업의 실행 분기는 폐기한다. 해당 작업을 복구하거나 대체 예약을 만들지 않고, 과거 heartbeat의 중복 방지 답변·`DONT_NOTIFY` 같은 종료 형식을 goal 답변에 사용하지 않는다. 과거 예약 실행·운영 수정 기록은 이력으로 보존하되 현재 지침으로 다시 실행하지 않는다. 별도 점검 채팅은 진행 중인 연구의 `next_action`·실행 핸들·결과·원장을 대신 갱신하지 않는다.

현재 편성분이 부족하면 제9.1절에 따라 필요한 실험을 구체화해 최소 증액·예약 후 수행한다. 잔여0만으로 승인 대기나 연구 중단 상태로 두지 않는다. 구체적 실험 근거가 없으면 허용된 분석으로 다음 판단을 정하고, 실제로 사용자 입력이나 외부 변화가 있어야만 가능한 범위 변경은 필요성과 그때의 행동을 한 번 기록한다. 같은 장애를 새 발견처럼 반복 보고하지 않는다.

제11절을 모두 충족하면 최종 한국어 보고서와 검수한 Word를 제공하고 `research_state.json`에 연구 산출물 완료를 기록한다. 이후 자동 실행에서는 완료한 연구를 다시 시작하지 않는다. 조건을 충족하지 못했다면 미완료 항목을 남기고, 문서만 길게 다시 작성하여 완료 처리하지 않는다.
