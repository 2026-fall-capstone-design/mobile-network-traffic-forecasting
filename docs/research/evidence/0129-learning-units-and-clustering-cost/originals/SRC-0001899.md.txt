# clustering의 효과를 현재 RCTL에 연결하는 방법

2026-09-26 추가 검토. 이번 문서는 최종 추천안이 아니라, 연구 방향을 정하기 위해 바로잡은 근거와 계산을 설명합니다.

**clustering 선행연구에서 정확도가 좋아졌다는 사실만으로, 현재 RCTL에도 같은 효과가 생긴다고 볼 수는 없습니다. 무엇을 하나의 sample로 만들고, 모델 하나가 무엇을 출력하는지부터 맞춰야 합니다.**

## 1. 비슷해 보이는 세 연구가 실제로 묶는 대상은 다릅니다

| 방식 | 묶는 대상 | 예측 방식 | 현재 연구에 주는 의미 |
|---|---|---|---|
| 현재 clustering → RCTL | 기존 cell | cell 하나의 입력으로 그 cell의 다음 값 예측 | 같은 모델에 어떤 cell의 sample을 함께 학습시킬지 결정 |
| Cash 등의 네트워크 traffic-matrix 연구 | 출발지–도착지 사이의 flow | 여러 flow를 한꺼번에 입력하고 여러 다음 값을 출력 | 분할하면 입력·출력 차원과 모델 수가 함께 달라짐 |
| Ma 등의 Validation-Driven Clustering | 여러 도로 센서를 포함한 하루 기록 | 하루 안의 여러 센서 값을 함께 예측 | sensor clustering이나 cell clustering의 직접 결과가 아님 |

Cash 등의 [2026년 논문](https://arxiv.org/html/2604.26081v1)은 무작위 분할에서도 성능이 좋아지는 경우를 보여 줍니다. 따라서 “어떤 대상을 묶었는가”와 “예측 문제를 여러 모델로 나눴는가”를 비교해야 한다는 근거가 됩니다. 다만 대표 성능표는 방법별로 선택한 cluster 수가 다릅니다. GÉANT에서는 histogram 40개, ACF·PSD 100개, 무작위 50개입니다. 같은 cluster 수로 비교한 소속 유사도 분석과 구분해서 읽어야 합니다.

[Validation-Driven Clustering](https://arxiv.org/html/2604.13748v1)의 PEMS-BAY 실험은 325개 센서를 포함한 하루 기록 180개를 묶습니다. 이 논문은 validation 오차를 기준으로 소속을 바꾸고, 특화 모델이 불리하면 global 모델을 사용합니다. 그 판단 원리는 참고할 수 있습니다. 그러나 현재 목표는 기존 cell의 소속을 정하고 RCTL과 분리하여 clustering을 실행하는 것이므로, 해당 방법을 그대로 옮긴 설계와는 다릅니다.

## 2. 작은 모델 여러 개가 전체적으로도 작은 것은 아닙니다

여러 값을 동시에 출력하는 GRU를 cluster별로 나누면 각 모델의 입력은 작아집니다. 하지만 recurrent core는 모델 수만큼 늘어납니다. hidden width를 그대로 두면 전체 parameter 수가 오히려 커질 수 있습니다.

예를 들어 한 층 GRU, hidden width 200, 선형 출력층을 가정하면 144개 flow를 한 모델로 처리할 때 약 24만 parameter가 필요합니다. 이를 21개 모델로 나누면 합계는 약 266만 개입니다. **이 수치는 명시한 구조에 대한 계산이며 저자 checkpoint의 측정값은 아닙니다.** 같은 width로 여러 모델을 만든 비교에서는 소속의 효과와 전체 용량의 효과를 함께 살펴야 합니다. [계산에 사용한 GRU 정의](https://docs.pytorch.org/docs/2.14/generated/torch.nn.modules.rnn.GRU.html)

현재 RCTL은 이와 다릅니다. 한 sample은 항상 한 cell의 입력이고, 출력도 한 개입니다. cluster가 커지면 입력 열이 많아지는 것이 아니라 학습할 sample이 많아집니다. 따라서 “많은 cell을 한 모델로 처리하니 출력 벡터가 너무 크다”는 설명은 현재 구조에 적용되지 않습니다.

## 3. cluster 수와 실제 계산량을 따로 봅니다

현재 코드와 같이 cell당 672개의 sample을 한 epoch에 모두 학습한다면, 10,000개 cell의 총 처리량은 672만 행입니다. cluster가 1개든 4개든 이 sample 수는 같습니다. batch 크기 256일 때 균형 분할의 update 수는 다음과 같습니다.

| cell 수 | cluster 1개 | cluster 4개 | cluster 16개 |
|---:|---:|---:|---:|
| 128 | 336회 | 336회 | 336회 |
| 1,024 | 2,688회 | 2,688회 | 2,688회 |
| 10,000 | 26,250회 | 26,252회 | 26,256회 |

위 표는 한 epoch의 산술값입니다. 수렴에 필요한 epoch, batch 크기에 따른 실행 효율, 모델 호출 overhead에 따라 실제 시간은 달라집니다. 모델 수를 줄이는 효과를 주장하려면 저장량, 호출 수, 학습시간 중 어떤 비용이 줄었는지 구체적으로 제시해야 합니다.

TabICLv2의 준비 비용도 포함해야 합니다. cell당 context 504개와 query 168개를 한 번 사용하는 설정을 10,000개 cell로 확대하면 context 준비는 10,000회, query는 168만 행입니다. 129개 분위수 결과만 float32로 보관해도 약 0.87 GB가 필요합니다. 이는 실제 대규모 실행 결과나 전체 메모리 사용량이 아니라, 기존 설정에 대한 규모 계산입니다.

## 4. 앞으로의 설계에 적용할 판단

현재 연구에서 입증할 핵심은 **같은 RCTL 구조와 비교 조건에서, TabICLv2가 함께 학습할 cell을 더 유용하게 정하거나 그 판단 비용을 줄여 주는가**입니다. 다른 논문의 다중 출력 분할이나 하루 기록 clustering을 그대로 성공 근거로 사용하지 않겠습니다.

같은 cluster 수에서 소속을 비교하는 평가와, cluster 수를 달리하며 정확도·비용을 비교하는 평가를 구분합니다. 기존 global RCTL과 단순 분할의 결과도 그대로 유지합니다. TabICLv2가 들어간다는 사실이나 cluster가 줄었다는 사실만으로 신규성과 비용 이득을 주장하지 않습니다.
