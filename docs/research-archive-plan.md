# TabICL 전체 연구기록 정리 계획

작성일은 2026년 10월 8일이다. 팀원이 과거 연구를 찾아 같은 조건의 실험을 중복하지 않고, 기존 결과를 재사용하며, 새 실험의 차이를 설명할 수 있는 연구기록 체계를 만든다. 모든 과거 기록을 검토 범위에 포함하고, 원문과 근거를 보존하면서 연구 문제별 설명으로 연결한다.

이 계획의 실행 방식은 하나의 지속적인 Goal 아래에서 작은 작업 묶음을 처리하고, 매번 파일 저장과 검수를 마친 뒤 다음 묶음으로 이어가는 것이다. 현재 문서는 실행 계획이며, 여기 적힌 전수 조사·분류·검수 완료를 이미 수행했다는 뜻은 아니다. 실제 실행에 사용할 프롬프트는 [연구기록 정리 Goal 프롬프트](research-archive-goal-prompt.md)에 있다.

## 1 목표와 완료 범위

팀원이 정리본에서 다음 질문에 답할 수 있어야 한다.

1. 이 연구 문제와 비슷한 시도가 이미 있었는가?
2. 당시 가설과 실제 구현은 무엇이었고, 어떤 자료와 조건을 사용했는가?
3. 실제 실행한 실험, 계획만 작성한 실험, 기존 결과를 다시 분석한 작업은 무엇인가?
4. 무엇이 개선되거나 악화됐고, 어떤 이유로 진행·보류·기각했는가?
5. 코드·설정·예측 출력·지표 중 무엇을 재사용할 수 있는가?
6. 같은 방법을 다시 검토하려면 어떤 조건이나 연구 질문이 달라져야 하는가?

전체 기록의 조사와 읽기, 연구 단위의 연결, 팀용 Markdown 작성, 재사용 자료 안내, 누락·모순 검수를 완료 범위로 잡는다. 현재 후보와 가까운 기록을 먼저 다루더라도 나머지 고유 기록을 생략하지 않는다. 성능이 좋았던 시도와 실패·보류·미실행 기록에 같은 추적 기준을 적용한다.

기존 모바일 네트워크 트래픽 예측 프로젝트의 모델 선정 상태는 유지한다. TabICLv2 연구 이력을 공유하는 것이 곧 팀의 최종 모델이나 연구 방향을 확정하는 결정은 아니다.

## 2 계획 수립 시 확인한 자료 규모

아래는 2026년 10월 8일 파일 목록을 확인한 결과다. 각 폴더 바로 아래의 파일 수이며, 전체 하위 폴더와 압축파일을 포함한 최종 조사 수가 아니다. 파일 수와 실험 수는 다르다.

| 위치 | 확인한 규모 | 정리할 때의 의미 |
|---|---:|---|
| `output/docx` | Word 27개 | 개정 관계와 각 문서의 고유 내용 확인 |
| `output/pdf` | PDF 19개와 기타 파일 4개 | Word 대응본·알고리즘·고유 자료 구분 |
| `output/pptx` | 발표자료 3개 | 그림·수식·발표용 해석의 추가 내용 확인 |
| `output/research` | Markdown 63개와 기타 파일 3개 | 보고서와 판단 근거의 상호 연결 |
| `output/research` 하위 | 스냅샷 폴더 45개, 기타 폴더 2개 | 동일 사본과 당시 버전에만 남은 내용 구분 |
| `tmp/redesign_20260925` | Markdown 1,202개, Python 1,261개, JSON 104개, PowerShell 1개 | 계획·실행·검수·복구·문서 생성 코드를 구분 |
| `tmp` 하위 | 폴더 41개 | 핵심 연구 폴더 외 제안서·미팅·수식·구현 수정 이력 포함 |

주요 폴더의 번호가 붙은 Markdown에는 1부터 642까지의 번호 중 632개가 나타났다. 번호가 비어 있다는 이유만으로 자료 누락을 확정하지 않는다. 다른 이름·형식·스냅샷에 존재할 수 있으며, 애초에 파일을 만들지 않은 번호일 수도 있다.

기존 `candidate_decision_index.md`는 약 439 KB, `progress.md`는 약 829 KB, `research_focus.md`는 약 518 KB다. 이 파일들을 매 회차 통째로 읽는 방식은 피하고, 제목·기록 번호·원문 위치를 유지해 나눠 읽는다. 기존 색인은 길잡이로 활용하되, 색인에 있다는 이유로 원문 검토를 완료 처리하지 않는다.

## 3 입력과 출력의 위치

원본 연구자료의 기준 경로는 다음과 같다.

`C:/Users/jungj/OneDrive/Desktop/연구실/Tab-ICL`

정리본을 작성할 기존 저장소의 Windows 접근 경로는 다음과 같다.

`//wsl.localhost/Ubuntu/home/jungjun0708/tabicl-traffic-forecasting`

같은 저장소의 WSL 경로는 `/home/jungjun0708/tabicl-traffic-forecasting`이다. 현재 연결된 원격 저장소는 `2026-fall-capstone-design/mobile-network-traffic-forecasting`이며, 실행 시작 시 실제 Git remote와 작업 상태를 다시 확인한다.

원본 폴더를 기준으로 루트 파일, `output`, `tmp`, 과거 첨부자료, 스냅샷, 압축파일 안의 연구자료까지 조사한다. 링크로 연결된 다른 위치의 자료는 먼저 참조 대상으로 등록하고 접근 가능한 범위에서 확인한다. 원본에 없는 과거 대화 전체를 확보했다고 가정하지 않는다.

기존 연구의 `research_state.json`, `research_focus.md`, `progress.md`, 실행 예산 원장과 Goal은 역사적 근거다. 정리 작업의 상태는 저장소의 별도 `.research-archive/`에 둔다. 기존 연구의 다음 실험·예산·완료 상태를 정리 작업 때문에 갱신하지 않는다.

## 4 전수 정리에서 구분할 네 가지 단위

| 단위 | 정의 | 예시 |
|---|---|---|
| 파일과 버전 | 실제 파일 또는 압축파일 내부 항목 | 같은 보고서의 Word·PDF·수정본 |
| 내용 구간 | 실제로 읽고 위치를 확인할 수 있는 원문 부분 | Markdown 절, Word 표, PDF 페이지, 코드 함수 |
| 연구 기록 | 질문·계획·실행·분석·판단 중 하나를 남긴 기록 | 기록 635의 실행 실패, 638의 정밀도 검수 |
| 연구 시도 | 같은 문제와 방법을 검토한 연결된 작업 묶음 | 계획→실패→복구→소속 확정→RCTL 확인 |

한 파일에 여러 기록이 있을 수 있고, 여러 파일이 한 시도를 설명할 수 있다. 따라서 파일마다 요약 한 개를 만드는 작업만으로 연구 이력이 완성되지는 않는다.

기존 번호는 보존하고 새 관리 ID를 추가한다. 새 ID를 실제 과거 실험 ID처럼 표현하지 않는다. 파일 이동이나 이름 변경으로 참조가 끊어지지 않도록 ID와 경로를 분리한다.

## 5 기록의 포함과 중복 처리 기준

모든 발견 파일에는 처리 이유를 남긴다. 연구 내용이 아닌 항목도 조용히 무시하지 않고 분류 근거를 기록한다.

| 자료 | 처리 기준 |
|---|---|
| 연구 메모·계획·결과·판단 | 고유 내용을 전부 읽고 관련 연구 기록에 연결 |
| 사용자 작성 연구 코드 | 목적·입출력·설정·실행 결과와 연결하고, 결론을 좌우하는 구현을 확인 |
| 실행 로그·JSON·CSV·배열 | 실행 여부·조건·수치·재사용 가능성을 확인하는 증거로 연결 |
| Word·PDF·발표자료·HWP | 본문·표·수식·그림·주석 등 고유 내용을 확인하고 원본 위치 보존 |
| 스냅샷·백업·ZIP | 내부 목록을 조사해 동일 사본과 해당 버전의 고유 내용 구분 |
| 문헌과 참고 구현 | 서지·역할·연구에서 검토한 내용과 위치를 기록하고 원문 링크 연결 |
| 문서 생성·렌더링 코드 | 연구 방법 구현과 구분해 문서 출처·변환 과정으로 연결 |
| 라이브러리·가상환경·빌드 캐시 | 연구 기록에서 제외한 이유와 식별 범위를 기록; 수정된 연구 코드가 섞였는지 확인 |
| 예약 작업·Goal·에이전트 운영 기록 | 연구 내용에 영향을 준 결정은 연결하고, 나머지는 운영 이력으로 구분 |

바이트 단위 SHA-256이 같은 사본은 대표 원문을 한 번 읽고 모든 사본을 연결할 수 있다. 해시가 다른 파일을 제목이나 텍스트 유사도만으로 같은 사본으로 판정하지 않는다. Word와 PDF가 같은 본문처럼 보여도 표·수식·그림·주석·변경 이력을 확인한다. 유사한 개정본은 변경 부분을 대조하되, 이전 버전에만 남은 고유 내용을 보존한다.

큰 ZIP이나 스냅샷은 파일 목록과 크기부터 확인하고 필요한 항목을 별도 작업공간에서 다룬다. 압축 내부 경로도 원본 ID와 연결한다. 원본을 삭제하거나 재배치해 중복을 제거하지 않는다.

## 6 최종 산출물

다음은 실행 시 만들 구조다. 이 계획에서 제안한 파일이 이미 생성됐다는 뜻은 아니다.

```text
docs/research/
  README.md                    팀원이 처음 읽는 안내와 현재 상태
  history.md                   연구 방향이 바뀐 이유와 전체 흐름
  prior-attempts.md             새 실험 전 확인하는 문제별 과거 시도 색인
  open-questions.md             아직 확인하지 못한 질문과 재검토 조건
  glossary.md                   cell·sample·context·query 등 용어
  topics/                      연구 문제별 종합 설명
  records/                     개별 연구 기록과 연결된 연구 시도
  references/                  문헌 비교와 구현 출처
  evidence/                    작은 결과표·설정·소속·지표·근거 발췌
  sources/                     팀이 열 수 있는 원문 또는 읽기용 변환본
  catalog/                     원본·중복·관계·검토 범위의 기계 판독 목록
  verification/                누락·수치·모순·링크 검수 결과
  templates/                   후속 실험 설계와 결과 기록 양식
scripts/research_archive/       목록·연결·검수에 필요한 최소 도구
.research-archive/             로컬 작업 상태와 변환 중간물
```

기존 `docs/progress/`는 앞으로의 팀 실험·회의 기록을 계속 남기는 위치로 활용한다. 과거 연구 색인을 이 안내와 연결하고, 기존 실험 이슈 양식에는 관련 과거기록과 새 실험의 차이를 적는 항목을 보완한다.

큰 데이터·체크포인트·대용량 캐시는 원본 위치와 해시, 생성·입수 방법, 팀 공유 위치를 연결한다. 단순한 개인 PC 경로만으로 팀 접근이 가능하다고 처리하지 않는다. 핵심 판단에 필요한 작은 근거는 정리본에 포함한다. 외부 논문은 서지·검토 내용·정식 링크를 중심으로 연결하고 라이브러리 전체나 다운로드한 논문 전체를 일괄 게시 대상으로 삼지 않는다.

읽기용 변환본의 링크는 저장소 상대경로나 팀이 접근할 수 있는 위치로 바꾼다. 보존용 원본은 바이트 그대로 두고, 링크를 보정한 사본과 구분한다. 팀용 안내문에서 기존 개인 PC 경로를 클릭해야만 근거를 확인할 수 있는 상태를 남기지 않는다.

## 7 원본 목록과 검토 이력의 필드

필드 이름은 구현 때 간소화할 수 있지만 아래 정보는 유지한다. 작은 상태 파일과 큰 원본 목록을 분리해 매 회차 전체 목록을 다시 읽지 않아도 되게 한다.

| 정보 | 필수 내용 |
|---|---|
| 원본 식별 | source_id, 원본 루트 기준 경로, 형식, 바이트 크기, 수정 시각, SHA-256 |
| 버전 관계 | 정확한 중복의 대표 ID, 개정 묶음 ID, 이전·이후 버전, 연결 근거 |
| 내용 유형 | 계획·실행·분석·판단·문헌·코드·운영 등 복수 역할 |
| 내용 위치 | 절·줄·표·페이지·그림·JSON key·코드 함수와 해당 원본 버전 |
| 검토 상태 | 발견·분류·추출·부분 검토·본문 검토·근거 검수·통합·수정 필요 |
| 범위 | 전체 내용 구간 수, 읽은 구간, 남은 구간, 추출 오류·읽기 불가 구간 |
| 연구 연결 | 기존 기록 번호, 새 record_id, 문제 ID, 시도 ID, 실행 결과 ID |
| 팀 접근 | 정리본 경로, 보존 원본 위치, 공유 가능한 증거 경로, 접근 미확인 사유 |
| 판단 근거 | 요약·결론에 사용한 주장 ID와 원문 위치 |
| 작업 기록 | 검토 회차, 검수 결과, 변경 감지, 후속 확인 |

한 개의 `done` 값으로 모든 상태를 합치지 않는다. 예를 들어 본문은 모두 읽었으나 실행 결과 파일이 없으면 `본문 검토 완료 / 결과 근거 미확보`로 표시한다. 자료에 기록되지 않은 값, 해당하지 않는 값, 아직 읽지 않은 값을 구분한다.

## 8 개별 연구 기록의 작성 양식

각 연구 기록은 다음 내용을 담는다. 모든 항목을 길게 채울 필요는 없지만, 빠진 정보를 추정해서 보충하지 않는다.

1. 기록 ID, 원래 번호·제목·날짜, 원문과 연결된 파일.
2. 해결하려던 연구 질문과 그 질문이 생긴 관측.
3. 제안한 원리, 실제 구현한 방법, 두 내용 사이의 차이.
4. 계획만 작성했는지, 일부 실행했는지, 완료했는지, 저장 결과만 재분석했는지.
5. 데이터 출처·버전, cell 집합, 기간·해상도, context와 query, 학습·검증·평가 범위.
6. 입력 특징·정규화, K·제약·후보 검색, 모델·가중치·seed·환경·실행 명령.
7. 비교군과 비교 조건의 차이, 평가 지표·척도·집계 방법.
8. 실제 결과, 반례와 실패 사례, 실행 비용과 재사용한 계산.
9. 당시 결론과 그 결론을 지지하는 범위.
10. 나중 기록에서 수정되거나 철회된 내용, 수정 이유와 원문 근거.
11. 재사용 가능한 코드·설정·소속·예측·결과와 사용 조건.
12. 동일한 실험을 반복하지 않아도 되는 이유와 다시 검토할 조건.
13. 후속 연구 기록과 미해결 질문.
14. 본문·코드·결과 중 확인한 범위, 모순·근거 공백, 검수 상태.

계획·코드·로그·결과·해석이 서로 다르면 각각의 증거가 말하는 범위를 적는다. 코드는 실행 가능성을 보여 줄 뿐 실제 실행을 증명하지 않는다. 최신 보고서라는 이유만으로 당시 실행 로그의 조건을 덮어쓰지 않는다.

## 9 주장과 수치의 근거를 연결하는 방법

요약의 주요 문장에는 최소한 한 개의 원문 위치를 연결한다. 정량 결론은 모델 이름과 수치만 옮기지 않고 아래 비교 단위를 함께 보존한다.

`대상 cell + 시간 구간 + 데이터/정규화 + 소속 선정 방식 + 최종 예측기 + seed + 지표 + 집계 방식 + 비교 기준`

예를 들어 Tab의 직접 예측 MAE, 소속 결정용 query 점수, 그 소속에서 학습한 RCTL의 MAE는 다른 결과다. 원단위 MAE와 cell별 정규화 MAE도 구분한다. 서로 다른 지표를 같은 성능표의 동등한 값으로 병합하지 않는다.

주장별로 `관측 사실 / 해석 / 원인 가설 / 제안 / 미확인`을 구분한다. 수치는 가능하면 저장된 JSON·CSV·배열과 대조하고, 비교 방향·분모·앞뒤 기간·반올림도 확인한다. 필요한 경우 저장 결과를 읽는 작은 계산으로 검수할 수 있으나 새로운 모델 학습이나 예측은 수행하지 않는다. 과거 코드의 실행 명령을 발견했다고 실행하지 않는다.

근거 파일이 없으면 보고서에서 주장한 수치로 표시하고 검증된 실행 결과로 승격하지 않는다. 자료만으로 해결할 수 없는 모순은 양쪽 근거와 함께 남긴다. 최신 문장에 맞추려고 원래 수치를 바꾸지 않는다.

## 10 단계별 실행 계획

### 단계 0 범위와 작업공간 확정

원본 루트와 현재 저장소, 적용 지침, Git 상태를 확인한다. 기존 변경을 보존하고 작업용 브랜치가 필요하면 `codex/research-archive` 계열의 이름을 사용한다. 원본과 정리 작업공간을 분리하고 조사 기준 시점을 기록한다. `.research-archive/`의 중간물은 팀 문서와 분리해 Git 제외 여부를 명시한다.

산출물은 범위 명세, 원본 경로 매핑, 최소 상태 파일이다. 기존 연구의 상태·원장과 혼동되지 않는 것을 확인하면 다음 단계로 간다.

### 단계 1 전체 목록과 버전 관계 조사

루트 전체를 재귀적으로 열거하고 ZIP 내부 항목, 스냅샷, 숨겨진 과거 첨부자료도 조사한다. 크기·형식·경로로 1차 분류하고 연구자료의 해시를 계산한다. 라이브러리·캐시 제외는 경로와 이유를 남긴다. 번호가 없는 연구자료도 포함한다.

파일 번호, 내부 링크, 코드·결과 디렉터리 이름을 교차 확인해 원본 간 관계 후보를 만든다. 번호 누락과 끊어진 링크는 조사 항목으로 등록한다. 이 단계에서 제목 기반 임시 분류는 가능하지만 연구 결론을 확정하지 않는다.

산출물은 전체 원본 목록, 중복·개정 관계, 임시 연구 기록 목록, 접근 오류 목록이다. 발견 항목마다 처리 경로가 지정돼 있어야 한다.

### 단계 2 소수의 서로 다른 사례로 양식 검증

6~10개의 연구 묶음을 골라 끝까지 처리한다. 최근 성과만 고르지 않고 초기 가설, 과학적 부정 결과, 구현 실패·복구, 계획만 있는 기록, 문헌 검토, 수치 수정, 여러 개정본이 있는 사례를 포함한다.

파일 수, 본문 길이, 근거 수, 처리 시간, 수정 필요 항목을 측정한다. 원문→연구 기록→문제별 요약의 연결이 유지되는지 확인하고 누락되는 필드가 있으면 양식을 고친다. 이는 정리 방식의 시범 적용이며 새 연구 실험이 아니다.

산출물은 양식, 시범 정리본, 검수 결과, 이후 작업량의 근거 있는 추정이다. 시범 적용 결과를 이용해 묶음 크기를 조정한다.

### 단계 3 고유 내용 전수 읽기와 기록 작성

연구 문제와 참조 관계를 기준으로 묶되, 전체 미처리 목록에서 차례대로 처리해 오래된 기록이 밀리지 않게 한다. 첫 기준은 회차당 3~5개 연구 묶음이며 복잡한 묶음은 1개만 처리해도 된다. 짧고 단순한 기록은 검수 여유가 있을 때 확대한다. 묶음 수를 채우려고 본문이나 근거를 생략하지 않는다.

매 묶음에서 계획·실행·복구·분석·판단을 연결하고 코드·결과를 확인한다. 큰 파일은 절별로 나누어 모든 구간을 읽는다. 도구 출력이 잘리면 미확인 부분을 별도로 읽고, 파일을 열었다는 사실만으로 완료 처리하지 않는다.

개정본에만 남아 있는 내용과 불리한 결과도 기록한다. 같은 원리를 다른 이름으로 제안한 경우 연구 계보에서 연결하되, 입력·목표·조건이 달라진 부분은 남긴다.

### 단계 4 근거 검수와 모순 정리

모든 정리 기록의 주요 결론·실행 상태·방법의 기각 범위를 원문과 대조한다. 성능 개선·악화, 신규성, 방법 기각, 후속 방향을 바꾼 수치는 관련 저장 결과까지 전수 대조한다. 도구가 확인한 파일 존재·해시·링크와 사람이 읽듯 확인해야 할 해석을 구분한다.

모순은 조건 차이, 구현 결함, 정정, 비교 대상 차이, 근거 부재 중 무엇인지 판별한다. 해결한 모순은 어느 근거로 해결했는지 기록하고, 해결하지 못한 모순은 최종 문서에도 남긴다. 일부 기록만 추려 검수한 것을 전체 검수로 표현하지 않는다.

### 단계 5 문제별 연구 이력과 중복 연구 방지 색인

전수 기록을 바탕으로 문제별 설명을 작성한다. 출발 분류로는 분포 거리, 시간 특징, context 교체·공동 자료, UPC 소속 수정, profile 비교, 후보 검색·표현 재사용, 자료 구성, 최적화·수치 보정, 강한 HGB 비교, 관계 점수, 고정 소속의 RCTL 효용, 확장 비용 등을 사용할 수 있다. 이 분류는 자료를 읽으며 수정하고, 모든 기록을 억지로 최신 알고리즘의 계보에 넣지 않는다.

각 문제에서 최초 질문→다른 접근→결과→판단 변경→남은 질문을 연결한다. `prior-attempts.md`에는 방법의 별칭, 주요 조건, 결론, 재사용 자료, 재검토 조건을 넣는다. 검색어가 달라도 같은 시도를 찾을 수 있도록 별칭을 남긴다.

### 단계 6 팀이 사용할 문서와 자료 묶음 구성

처음 읽는 안내, 용어, 현재 후보, 연구 흐름, 과거 시도 색인, 미해결 질문을 서로 연결한다. Word·PDF의 개인 PC 링크를 읽기용 문서에서 교체한다. 핵심 증거의 팀 접근 경로를 확인하고, 아직 연결되지 않은 대용량 자료는 상태를 명시한다.

재사용할 코드에는 함께 필요한 로컬 모듈·설정·환경 정보를 연결한다. 코드 보관 완료와 현재 환경에서의 재현 성공을 구분한다. 아카이브 작성 과정에서 실행하지 않은 코드는 `재실행 미확인`으로 표시한다.

기존 이슈 양식에는 관련 과거 기록, 이전 시도와 다른 점, 재사용할 결과, 결과별 판단을 보완한다. 과거 모든 기록을 각각 GitHub Issue로 생성하지 않고, 앞으로 수행할 작업을 중심으로 이슈를 사용한다.

### 단계 7 전체 범위와 사용성 최종 검수

원본에서 정리본으로, 정리본에서 원본으로 양방향 추적을 확인한다. 원본 목록의 모든 고유 연구 내용이 정리본에 반영됐는지 검사하고, 모든 핵심 결론의 출처를 역으로 연다. 링크·ID·표의 수치·상태 집계를 검사한다.

팀원 관점의 대표 질문 10개 이상을 골라 기존 시도와 실행 조건, 결과, 재검토 조건을 찾을 수 있는지 확인한다. 방법의 실패와 구현 실패를 구분하는 질문, 완료 실행과 캐시 재분석을 구분하는 질문도 포함한다.

마지막으로 원본 목록을 다시 비교해 조사 중 새로 생기거나 변경된 자료를 확인한다. 변경분은 별도 목록으로 처리하고, 기준 시점 이후 자료를 누락한 채 전체 최신 상태라고 표현하지 않는다.

완료 산출물은 검수된 저장소 문서, 근거 연결, 범위 보고서, 남은 공백 목록과 GitHub 기본 브랜치에 병합된 결과다. 2026-10-09 사용자 요청으로 게시·PR 생성·병합까지 실행 범위에 포함했다. 로컬 저장, PR 게시, 검사 통과, 원격 병합을 구분해 보고한다. 구체적인 절차는 18절을 따른다.

## 11 긴 작업에서 품질을 유지하는 실행 규칙

### 답변 길이와 실제 작업량을 분리한다

한 번의 출력 길이, 한 번에 참고할 수 있는 문맥, 전체 작업에 드는 사용량은 별개의 제약이다. 정확한 수치는 모델과 환경에 따라 달라 이 계획에서 임의의 토큰 상한을 정하지 않는다. 결과를 여러 파일에 나누어 저장할 수 있으므로 전체 연구 정리를 한 답변에 넣을 필요는 없다.

Goal은 여러 회차에 걸친 목표 유지에 적합하다. 사용량·중단·실행 환경 조건의 영향을 받으므로 무제한 실행이나 자동적인 품질 보장을 의미하지는 않는다. [OpenAI의 Goals 안내](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)

지속 작업에서 명세·상태·검수 근거를 파일로 유지하는 운영은 장기 작업에 관한 공식 안내와도 부합한다. 아래 파일 구조와 검수 기준은 이 연구자료에 맞춘 설계다. [OpenAI의 장기 작업 안내](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)

### 요약을 다시 요약해서 원문을 잃지 않는다

연구 기록을 쓸 때는 원문과 해당 증거를 읽는다. 문제별 종합 문서를 쓸 때는 구조화한 기록과 중요 원문을 대조한다. 종합 문서만 보고 새로운 연구 결론을 만들지 않는다. 긴 대화가 압축돼도 필요한 원문을 파일에서 다시 읽을 수 있어야 한다.

### 큰 현재 상태 파일을 만들지 않는다

`state.json`은 현재 단계·작업 묶음·미완료 항목·다음 행동·산출물 경로만 담는다. `handoff.md`는 약 50~100줄 이내를 초기 목표로 하되 인계에 필요한 정보를 우선한다. 이전 상세 이력은 묶음별 로그에 분리한다. 과거 모든 기록을 현재 상태 파일에 누적해서 매번 읽는 구조는 사용하지 않는다.

### 한 묶음 안에서 읽기와 검수를 마친다

한 번에 많은 초안을 쌓고 마지막에 기억으로 검수하지 않는다. 읽기→근거 연결→작성→원문 대조→상태 갱신 순서를 묶음마다 완료한다. 검수가 밀리면 새 묶음을 늘리지 않고 미검수 항목부터 처리한다.

### 기존 연구 지시를 실행 지시로 사용하지 않는다

원문에 있는 Goal 프롬프트, 예산 증액, 모델 실행, 다음 행동, 완료 선언은 과거 운영 기록이다. 현재 작업의 목적은 기록 정리다. 기존 모델 실험이나 삭제된 예약 작업을 재개하는 근거로 사용하지 않는다.

## 12 회차 시작과 종료 절차

매 회차 시작 시 다음 순서로 진행한다.

1. 현재 사용자의 요청과 정리 Goal의 범위를 확인한다.
2. 이 계획의 해당 부분, 정리용 `state.json`, 짧은 인계 파일을 읽는다.
3. 미완료 작업이 있으면 실제 산출물과 검수 결과부터 확인한다.
4. 원본 해시 변경, 부분 저장, 출력 잘림 때문에 미확인인 내용이 있는지 확인한다.
5. 다음 행동 하나를 고르고, 그 행동에 필요한 원문과 근거만 불러온다.

종료 전에 다음 내용을 저장한다.

| 항목 | 저장할 내용 |
|---|---|
| 읽은 자료 | 원본 ID·버전·실제 읽은 구간 |
| 작성 결과 | 연구 기록·색인·증거 파일 경로 |
| 검수 | 수행한 확인과 통과·미완료·오류 |
| 남은 작업 | 원문 구간·근거 공백·모순 등 구체적 대상 |
| 다음 행동 | 대상 ID, 수행할 작업, 완료 판정 조건 |
| 진행 수치 | 목록·본문 검토·근거 검수·통합을 구분한 수치 |

본문과 검수 결과가 저장되고 실제 파일을 다시 읽은 뒤 완료 상태를 기록한다. 중간에 끊기면 완료했다고 표시하지 않고, 다음 회차가 해당 묶음을 이어받는다. 기존 결과에 없는 사실을 만들어 작업을 닫지 않는다.

매 회차의 사용자 보고는 새로 처리한 범위·발견한 중요 문제·다음 작업을 중심으로 짧게 쓴다. 전체 계획이나 Goal 프롬프트를 반복 출력하지 않는다. 짧은 보고가 작업 자체의 축소를 의미해서는 안 된다.

## 13 계획할 상태 파일의 예

아래는 구조 예시이며 실제 진행 상태나 수량이 아니다.

```json
{
  "schema_version": 1,
  "project": "tabicl_research_archive",
  "phase": "inventory",
  "inventory_version": null,
  "active_batch": null,
  "pending_queue": "queue.jsonl",
  "last_verified_batch": null,
  "coverage_report": "coverage.json",
  "open_issues": "review-issues.jsonl",
  "next_action": {
    "targets": [],
    "operation": "원본 목록과 처리 범위를 확정한다",
    "done_when": "발견 항목에 ID와 처리 경로가 있고 접근 실패가 기록돼 있다"
  }
}
```

`pending_queue`의 모든 내용을 매번 문맥에 넣지 않고 현재 묶음만 읽는다. 완료 로그는 묶음별로 분리한다. 경로와 출력물이 있는지만으로 의미 검수가 통과했다고 계산하지 않는다. 파일 변경이 감지되면 그 원본에 의존하는 기록·주장을 재검토 대상으로 되돌린다.

작업 묶음의 상태는 `대기 → 원문 검토 중 → 근거 연결 중 → 검수 중 → 완료`로 구분한다. 중단됐던 `검수 중` 항목은 파일을 다시 확인한 뒤 이어받고, 무조건 원문 추출부터 재시작하지 않는다. 상태 저장 도중 끊긴 경우에는 실제 산출물·검수 파일을 대조해 복구한다. 상태 변경은 임시 파일에 쓴 뒤 교체하는 방식으로 구성하고, 한 작업공간의 상태를 여러 실행이 동시에 갱신하지 않게 한다.

## 14 검수 기준과 완료 조건

단일 완료율로 품질을 대표하지 않는다. 다음 지표를 나누어 보고한다.

| 지표 | 분모와 완료 기준 |
|---|---|
| 목록 처리율 | 발견한 전체 항목 중 포함·동일 사본·제외·접근 문제의 처리가 기록된 비율 |
| 고유 내용 검토율 | 포함된 고유 연구 내용 전체 중 실제 본문·표·수식·그림을 검토한 비율 |
| 근거 검수율 | 공개할 핵심 주장·수치 중 근거 대조를 완료한 비율 |
| 기록 통합률 | 확인한 연구 기록 중 문제·시도·후속 판단과 연결한 비율 |
| 팀 접근 확인율 | 공유가 필요한 근거 중 팀용 경로를 확인한 비율 |

정확한 중복·범위 제외·접근 실패는 서로 겹치지 않게 집계하고 각각의 이유를 기록한다. 미열람 고유 자료를 중복이나 제외로 돌려 완료율을 올리지 않는다. 세그먼트를 자동으로 잘게 나누어 내용 검토량이 늘어난 것처럼 보고하지 않는다.

전체 정리 완료를 선언하려면 다음을 만족해야 한다.

1. 원본 조사 범위와 기준 시점이 명확하고, 설명되지 않은 누락이 없다.
2. 포함된 고유 연구 기록의 전체 내용 검토가 끝났다. 읽지 못한 기록이 있으면 전수 검토 완료로 표현하지 않는다.
3. 주요 결론의 출처와 적용 범위가 연결돼 있고, 핵심 수치는 근거 대조 결과가 표시돼 있다.
4. 계획·실행·분석·구현 실패·과학적 부정 결과·정정·재사용을 구분했다.
5. 연구 기록마다 원문과 문제별 색인이 양방향으로 연결돼 있다.
6. 알려진 모순과 증거 공백을 숨기지 않았으며, 중요한 공백을 검증 완료로 표시하지 않았다.
7. 팀용 문서의 내부 링크가 유효하고 핵심 근거를 개인 PC 경로에만 의존하지 않는다.
8. 원본과 기존 연구 상태·예산 원장을 보존했다.
9. 사용자에게 최종 정리본·검수 결과·남은 불확실성을 함께 제시할 수 있다.
10. 2026-10-09 추가 요청에 따라 검수된 모든 정리본의 GitHub PR과 필수 검사를 확인하고 기본 브랜치 병합을 확인했다. 일부 묶음의 병합을 전체 정리 완료로 집계하지 않는다.

읽기 불가 원본이나 필수 근거 접근 문제가 남으면 다른 작업을 계속 진행하고, 해결 가능한 수단을 확인한다. 실제로 더 진행할 수 없을 때는 남은 범위와 필요한 조치를 구체적으로 보고한다. 사용량 종료·중단·접근 장애를 완료로 바꾸지 않으며, Goal 상태 변경은 해당 도구의 조건을 따른다.

자동 검수는 중복 ID, 존재하지 않는 source_id, 읽지 않은 구간의 완료 표시, 대표 원본 없는 중복, 근거 없는 수치 행, 모순된 분모, 팀용 내부 링크 단절 등을 탐지하도록 만든다. 문장 의미의 정확성을 자동 검사 통과로 대신하지 않는다. 원문 대조는 별도 단계에서 수행하며, 같은 에이전트의 두 번째 검토를 독립 연구자의 검증으로 표현하지 않는다.

## 15 실제 사례로 보는 잘못된 요약 방지

기록 635는 저장 함수 인자 충돌로 실행이 중단된 사례다. 이를 관계 점수 방법의 실증적 실패로 분류하면 팀원이 검토 가능한 방법을 잘못 포기할 수 있다. 따라서 `구현 오류 / 부분 실행 / 후속 복구 있음`으로 연결해야 한다.

기록 637에서의 일부 판단은 638의 정밀도 보정 전에 나온 상태다. 기록 638은 저장 예측을 다시 계산해 유효 관계와 소속을 확인한 작업이며, 새로운 관측이나 새로운 모델 예측을 생성한 것으로 세면 안 된다. 이전 상태와 수정 이유를 함께 보존한다.

기록 639의 평균 개선과 기간별 손해, 기록 641의 동일 출력 기반 대조는 각각의 조건과 역할로 기록한다. 같은 RCTL 결과를 여러 문서가 인용했다고 독립 실험 여러 개로 집계하지 않는다.

이 사례들은 정리 양식의 시험 대상으로 사용한다. 다른 과거 기록에도 같은 검토 기준을 적용한다.

계획 수립에서 직접 읽은 상세 근거는 원본 루트의 `tmp/redesign_20260925/635_bounded_relation_graph_findings.md`와 `638_bounded_relation_precision_findings.md`다. 639·641의 연결은 기존 진행 기록과 사용자가 지정한 두 문서에서 확인했다. 실제 아카이브 작성 시 각 상세 결과와 연결된 실행 산출물까지 읽고 검수 상태를 기록한다.

## 16 기간과 사용량을 추정하는 방법

아직 고유 기록 수와 자료별 난이도가 확정되지 않았으므로 전체 완료 시간이나 총 토큰 수를 단정하지 않는다. 첫 시범 묶음에서 순수 문서, 복구 이력, 수치 대조, 복잡한 개정본의 처리 시간을 각각 측정한다.

남은 작업량은 유형별 미처리 고유 기록 수와 실측 처리 시간을 곱해 범위로 추정하고, 모순·수치·접근 복구에 드는 추가 검수를 따로 제시한다. 1,202개 파일을 일정한 속도로 요약한다는 계산이나 642를 실험 수로 사용하는 계산은 하지 않는다.

사용량 제한에 도달하면 저장·검수한 범위와 다음 행동을 남긴다. 남은 예산 때문에 후기 기록의 검토 깊이를 줄이거나 이미 확인한 부정 결과를 생략하지 않는다. 모델 토큰 예산은 사용자가 수치를 명시한 경우에만 그 값으로 설정한다.

## 17 계획의 적용과 이후 운영

실행을 시작하면 먼저 단계 0~2에서 목록과 양식의 신뢰성을 확보하고, 이후 같은 기준으로 전체 고유 기록을 처리한다. 실행 중 작은 양식 개선은 버전과 이유를 남겨 적용하고, 기존 기록에 필요한 수정만 되돌려 반영한다. 개선할 때마다 처음부터 재조사하지 않는다.

이후 팀의 새 실험에는 관련 과거 기록, 새롭게 달라지는 조건·질문, 재사용한 결과, 결과별 다음 판단을 남긴다. 성능이 개선되지 않은 실험도 같은 방식으로 기록한다. 이 운영이 정착돼야 전체 과거기록 정리가 이후의 중복 연구 방지로 이어진다.

## 18 GitHub 반영과 병합 — 2026-10-09 실행 범위 추가

사용자는 `https://github.com/2026-fall-capstone-design/mobile-network-traffic-forecasting`에 GitHub 반영·PR 생성·병합까지 수행하도록 요청했다. 이 요청은 앞선 로컬 정리본 기본 범위를 확장한다. Goal은 전체 기록 정리를 계속하며, 검수된 묶음을 순차적으로 팀 저장소에 반영한다.

각 묶음은 원문 대조·수치·링크·보존 검수와 저장소의 관련 검사를 마친 뒤 `codex/` 브랜치에서 커밋하고 푸시한다. 실제 기본 브랜치와 최신 변경을 확인한 후 PR을 만들고 현재 대화에 연결한다. PR에는 완료한 연구 범위, 주요 한계, 확인한 검사와 남은 기록을 쓴다. CI·리뷰·병합 정책을 충족하면 병합하고, 기본 브랜치의 병합 커밋과 대상 파일을 확인한다. 필수 검사나 리뷰 조건을 우회하지 않는다.

첫 반영에는 전체 목록·처리 범위·검수 도구와 검수가 끝난 시범 기록을 포함할 수 있다. 나머지 시범 사례와 전체 기록은 후속 PR로 이어 간다. 개인 정리 상태는 `.research-archive/`에 유지하고, 팀에는 근거와 검토 현황을 저장소 문서로 제공한다. 각 PR의 URL·커밋·검사·병합 상태는 별도 정리 상태에 기록해 중단 후 중복 생성하지 않는다. 모든 내용 완료 조건과 최종 원격 병합 확인이 충족돼야 Goal을 완료한다.
